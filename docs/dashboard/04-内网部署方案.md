## 1. 交付边界

网站必须能在封闭局域网独立打开、刷新、重启和恢复。页面、Logo、脚本、样式、服务、数据库、字体与时区数据均来自内网或安装包；不依赖 Sites、Cloudflare、云数据库、CDN、Google Fonts、外部登录、在线许可证检查或互联网 DNS/NTP。文档里的外部链接是开发调查资料，不是运行依赖。

现有 `.openai/hosting.json` 只是早期工具识别的静态目录描述，不参与本方案启动，不需要 Sites 账户、站点编号或部署密钥。保留该元数据不使网站依赖外部实现；内网发布包只包含所需静态文件和本地服务。

建设时允许在联网开发／构建机准备依赖，再按现场规定带入内网；现场首次安装、冷启动和重启均不得临时联网下载。最终编单使用的模型也必须在内网，但本次网站方案不选模型、GPU 或采购型号，仍依原行动计划验证。

## 2. 当前原型怎样使用

已有完整静态目录 `src/dashboard/dist/`，包含 HTML、JS、CSS 和两份 PNG；无需 npm install、编译、数据库或云服务。从仓库根目录运行：

```sh
python3 -m http.server 8765 --bind 127.0.0.1 --directory src/dashboard/dist
```

这是本机预览，`127.0.0.1` 仅当前设备可访问，不等于局域网已发布。其他设备查看需由现场选定内网服务地址并限制访问；临时展示可以把同一目录交给内网现有静态 Web 服务。Python 的临时预览服务不作为真实业务长期部署方式。本次没有开放新端口或修改防火墙。

浏览器默认进入明天、浅色；`?theme=dark` 指定深色，`?channels=40` 验证扩容样式。当前刷新会重建虚构数据，没有真实状态落库。保留正在使用的本机预览服务供设计确认，退出展示后由启动者停止。

## 3. 真实状态网站的部署形态

首个状态服务验证环境采用一台 Linux 主机，网站和数据库在内网运行。最终两台主机能独立承担故障后的工作负载是既有交付方向，需另外通过 E13 的接管演练；单机验证不能被称作完整双机交付。

| 组件 | 位置与职责 | 对外连接 |
|---|---|---|
| 内网浏览器 | 展示大屏；使用设备已安装的中文系统字体 | 只访问内网站点 HTTPS |
| Nginx 网站入口 | 提供本地静态资源、内网 TLS、代理只读 API；长期运行入口 | 443 对获准展示终端开放 |
| API 服务 | Python＋FastAPI＋Uvicorn，生成快照、接入受控事件 | 浏览器仅经入口；内部事件端点单独限制来源 |
| worker | 与 API 同一版本代码镜像、独立进程；采集、任务状态、恢复、对比 | 仅访问获准数据库、文件来源及内网执行器 |
| PostgreSQL | 日单、事件、尝试、交接与证据索引 | 5432 不对展示终端开放，仅服务及主备复制使用 |
| 文件存储 | EPG 原件、原产出、最终文件与证据；独立版本、摘要校验 | 业务来源只读；锦书证据和约定 Output 按明确路径授权写入 |
| 内网模型／执行器 | 后续真实编单能力；与状态网站解耦 | 不由浏览器直接调用，不访问外部模型 API |

建议部署平台 Ubuntu 24.04 LTS，使用 Docker Engine＋Compose 管理网站、API、worker、数据库；现场主机架构与 OS 仍需核实。Mac 当前承担开发预览，不据此假定生产是 Apple Silicon。Windows 上 Playbox 的只读采集若需本机代理，作为独立适配器包交付；来源方式未验证前不安装，不把主服务迁到 Windows 来绕过验证。

API 和 worker 以不同入口运行同一个镜像；数据库、文件卷、配置独立于容器。数据库就绪后由维护身份执行一次迁移，再启动 API 和 worker；网站静态入口独立启动，即使 API 尚未就绪也能给出数据不可用说明，不把它绑死在数据库健康条件后。只用受支持的容器重启策略恢复进程，任务是否恢复仍由数据库租约与核对流程判断。

网站入口只代理明确的路径。读接口使用可撤销的只读设备／会话身份，网段限制作为额外边界；内部事件入口要求独立来源服务凭证及事件权限，不让所有大屏访问者写事件。内网 TLS 证书由内网 CA 或现场认可方式签发并预装信任，不能依赖外网 ACME。业务时间来自内网时间源或现场校时机制；没有 DNS 时用固定内网 IP 和对应证书，不依赖互联网解析。

### 3.1 访问、证书与容器网络

网站只发布443入口；API／数据库在容器专用网络，不向展示终端发布其服务端口。需要跨机复制或 Windows 适配器连接时，仅向明确对端开放所需入口，分别认证。不能只检查 UFW 配置就判定端口已隔离：Docker 发布端口的流量处理可能绕开 UFW 的预期路径，见[Docker 防火墙说明](https://docs.docker.com/engine/network/packet-filtering-firewalls/)。验收必须从允许和不允许的终端分别验证实际可达性，按采用的 iptables／nftables 网络后端配置，不能为修复连接直接禁掉 Docker 防火墙管理。

无人值守大屏的初始建议是由维护人员预配置本地设备证书，授予只读角色；服务来源使用各自可撤销凭证。具体认证方式在首个内网实施合同固定，不依赖外网登录、不向日常大屏用户反复弹登录。设备遗失或凭证撤销后拒绝访问；证书／凭证到期显示认证不可用，不继续显示“状态正常”。CA 信任、服务名或IP与证书 SAN 匹配、续期包、轮换步骤和维护责任一并交付。

反向代理清除外来身份／转发头，再写入由已验证连接产生的身份；API仅信任入口地址。应用容器使用非root用户、最小可写目录，不挂 Docker socket，不启用 privileged；只读业务来源挂载与证据／Output写入挂载分开。认证凭据使用受限文件或部署 secret，不能通过网页、URL参数或日志传递。

### 3.2 服务生命周期与容量

Compose 要配置数据库 healthcheck 和 `service_healthy` 依赖；迁移成功是 API就绪的独立条件；静态网站独立提供页面，对未就绪 API 返回明确不可用响应。官方明确容器启动不等于服务就绪，见[启动顺序](https://docs.docker.com/compose/how-tos/startup-order/)。`pg_isready` 仅证明数据库可接受连接，API还须核对schema版本和必要查询。

容器退出可按重启策略处理，unhealthy 本身不能当成必然自动重启；参见[Docker 重启策略](https://docs.docker.com/engine/containers/start-containers-automatically/)。数据库断开时 API 返回不可用、worker停止领取并重连；长时间重连失败或执行卡死要产生可见维护诊断，按受限重启／人工接续流程处理，不能无限重启重复业务动作。收到停止信号先停领、取消未开始请求、在有界宽限内结束／记录执行状态、关闭连接池；超时强停后按租约核对恢复。

为 API、worker、数据库和模型分别设置 CPU、内存和并发预算，给状态页和系统保留余量。容器默认不自动限制资源，见[Docker 资源约束](https://docs.docker.com/engine/containers/resource_constraints/)。日志轮换、WAL／备份空间、证据磁盘余量必须检查；写入空间不足时停止新增业务交付并说明原因，不删除未备份证据来腾空间。

容量记录至少包括：20／40频道、同时覆盖的播出日、同时运行的任务数、观看终端数、每快照字节数、每阶段事件量、三日和历史数据规模。按“终端数÷轮询间隔”估算平稳读请求量，再测试同时开机／重连峰值；按实际事件、索引、文件、备份及保留期估算存储。验证期间保持服务端资源、延迟、池等待和浏览器内存曲线，不能只证明第一屏能打开。参数由测量形成，不在本文承诺固定硬件能撑多少任务。

## 4. 依赖清单

### 4.1 网站与状态服务

| 层次 | 依赖 | 用途与离线准备 |
|---|---|---|
| 前端运行 | 现代 Chromium／Edge 等支持 SVG 和 CSS 动画的浏览器 | 安装包离线带入，固定验收版本；无需浏览器插件、CDN、在线字体 |
| 前端资源 | 当前 HTML、CSS、JS、SVG 代码、本地 PNG、系统中文字体 | 全量随包；中文字体不足时依法准备本地字体，不运行时下载 |
| 服务语言 | Python 3.12 系列 | 放入应用镜像，精确补丁号由构建清单锁定 |
| Web 框架 | FastAPI、Uvicorn | 前者提供接口，后者提供 ASGI 服务；不需要托管版 FastAPI 服务 |
| 数据验证／网络基础 | FastAPI／Uvicorn 解析出的 Pydantic、Starlette 等传递依赖 | 全部进入带哈希的锁文件及镜像，不能只带顶层包 |
| 数据库驱动 | Psycopg 3＋连接池组件 `psycopg_pool` | 初始候选 `psycopg[binary,pool]`；平台支持和自带 libpq 的版本随锁文件验证 |
| 数据库服务 | PostgreSQL 17 系列 | 服务镜像及 pg_dump／pg_restore 等配套工具；主备同主版本，补丁同步维护 |
| 入口与容器 | Nginx、Docker Engine、Compose 插件 | 完整镜像和匹配 OS 的离线安装包；Compose 本地启动禁止拉取与构建 |
| 系统基础 | CA 证书、时区数据库／tzdata、中文字体、必需共享库 | 放入 OS 离线包或镜像；不能依靠公网校时或下载根证书 |
| 开发／验证 | Git、Python、Node.js、pytest、HTTPX，后续契约／数据库测试工具 | Node.js 只运行现有前端模型测试；不随业务网页常驻。新增测试依赖在实现时锁定 |

当前静态网页没有 Python 第三方依赖；上述框架、驱动和数据库都是未来真实服务的依赖，仓库尚无 `pyproject.toml`、锁文件或镜像摘要，不能称离线安装包已经齐备。实现首个服务时必须同时提交 `pyproject.toml`、完整带哈希锁文件、镜像构建文件和可运行 Compose 配置，不允许以此文档代替可复现依赖。

Psycopg 官方区分自带库的 binary 安装和需编译／系统 libpq 的方式，因此安装包必须匹配现场 CPU／OS，不能把 Mac 缓存直接搬给 Linux；参见[安装文档](https://www.psycopg.org/psycopg3/docs/basic/install.html)。PostgreSQL 主版本有明确维护周期，17 系列当前仍受支持，最终构建采用当时已验证的受支持补丁；参见[版本政策](https://www.postgresql.org/support/versioning/)。Python 时区读取需要系统时区数据库或 tzdata 包，参见 [zoneinfo](https://docs.python.org/3.12/library/zoneinfo.html)。

### 4.2 属于完整编单而非网站的依赖

素材解析所需 ffprobe／FFmpeg、Excel／PLY 解析库、Agent SDK、模型推理服务、模型权重、GPU 驱动／运行库和 Playbox Windows 适配环境，按真实功能逐项引入和离线打包；当前不因为大屏画了某个节点就加入依赖或承诺能力。完整离线 E07 必须包含这些真实业务依赖；仅断网打开网页不能替代 E07。

接口文档也不能偷偷加载 CDN：生产关闭默认交互 API 文档页；需要维护文档时使用本地资产。FastAPI 官方说明了文档 UI 的[静态资产自托管方式](https://fastapi.tiangolo.com/how-to/custom-docs-ui-assets/)。大屏不加载统计、埋点、在线错误上报或任何第三方脚本。

## 5. 计划中的交付目录

下列是发布包格式约定，不是仓库已存在的安装产物。发布包放内网软件库，镜像、wheel、凭据和真实数据不进入 Git。

```text
jinshu-release/<release-id>/
  manifest.json          # 版本、Git SHA、schema 版本、OS/CPU、全文件 SHA-256
  manifest.signature     # 可信发布身份对清单的签名
  sbom.json              # 依赖清单、版本及许可证
  verification/          # 离线验证工具；信任公钥指纹另行可信分发
  images/               # app、postgres、nginx 及所需基础镜像的离线归档
  packages/os/          # Engine、Compose、字体、时区及完整依赖闭包
  packages/python/      # 锁文件对应 wheel；需要内网重建时使用
  config-templates/     # 无密钥模板、端口及挂载说明
  compose.yaml          # 固定本地镜像标签／摘要；禁拉取
  migrations/           # 与应用版本配套的有序 SQL
  scripts/              # preflight/install/start/stop/backup/restore/check
  docs/                 # 本方案、版本说明、离线操作与恢复手册
  licenses/             # 组件与字体／模型使用许可说明
```

计划中的运行目录：`/opt/jinshu/releases/<id>/` 放只读发布包，`/etc/jinshu/` 放仅维护人员可读的现场配置，`/var/lib/jinshu/` 放数据库卷与证据文件，`/var/log/jinshu/` 放轮换运行日志。备份放独立内网目标，不与主机唯一磁盘共存。实际 EPG、素材和业务 Output 使用命名挂载映射，不能把这些示例路径当成现场已批准目录。

配置至少包括业务时区、首批频道及编号、每日计划规则、截止规则版本、刷新／心跳／过期参数、服务监听与访问范围、数据库连接、各来源位置及只读／可写边界、证据存储位置、备份位置与保留策略。凭据独立注入，不放浏览器配置，不写入镜像或发布清单。

## 6. 离线安装和更新流程

1. 联网构建机核对目标 OS／CPU，解析并锁定全部依赖，构建网站与服务镜像，运行规则／数据库／契约检查。生成 manifest、依赖清单及漏洞检查结果，用批准发布身份签名；不使用浮动 `latest` 作为部署依据。
2. 导出所需镜像、安装包、wheel 和证书／时区／字体资源；逐项校验摘要。Docker 支持导出镜像归档，参见 [image save](https://docs.docker.com/reference/cli/docker/image/save/)。如现场需要 Python 包重建，按锁文件从本地 wheelhouse 使用 `--no-index --find-links` 安装，参见 [pip install](https://pip.pypa.io/en/stable/cli/pip_install/)。
3. 在没有互联网、没有现成镜像缓存的测试机完整安装一次。验证依赖闭包、字体、数据库初始化和重启；缺包视为交付失败，回构建侧补齐。
4. 现场使用预置信任公钥离线验证清单签名，再核对目标与每个软件包摘要，未知签名者、篡改或不匹配版本均拒绝安装。信任根不能只来自同一个待验证包；准备配置和指定卷；备份旧数据库与文件索引后再迁移。数据库迁移由维护入口单次执行，不能每个 worker 同时升级。
5. 加载本地镜像，完成健康检查后启动。计划采用 `docker compose up -d --no-build --pull never`，具体配置文件必须随实现交付；这些参数避免现场暗中构建／拉取，见 [Compose up](https://docs.docker.com/reference/cli/docker/compose/up/)。
6. 用内网浏览器打开网站并断开互联网验证首次加载、刷新、三日切换、深浅主题、来源中断与恢复；确认所有资源和 API 都指向本地或明确的内网服务。
7. 更新前暂停领取新任务、保存进行中状态和证据；更新后先恢复只读页面，再核对执行租约与外部交接，最后恢复 worker。每次迁移必须从上一已发布schema和含历史记录的副本演练，核对行数、关键约束与恢复；未知或超前schema拒绝启动worker。旧版本只在数据库模式兼容时直接切回；不兼容迁移按已演练的数据库＋文件备份恢复，不能只回滚镜像。

包内校验和只能帮助检验文件一致性，不能单独证明发布来源；制品与可信身份的结合参考 [SLSA 验证说明](https://slsa.dev/spec/v1.2/verifying-artifacts)。本项目只采用可在内网执行的签名／摘要验证，不声称达到某个 SLSA 等级。验证工具、公钥信任、失效／撤销密钥处理和可回退版本均须能离线使用。

断网不等于永久不更新。依赖清单覆盖传递包、基础镜像、OS、浏览器和必要运行库；构建侧定期检查支持周期及漏洞通告，将获准补丁、兼容性结果和离线安装包带入维护窗口。现场不访问在线扫描、透明日志或软件注册表来完成启动／验证；检查结果有日期，不能视为永不过期。

页面缓存策略：HTML 和实时接口禁止持久缓存；发布资产按版本或内容摘要区分，避免新版 HTML 配旧脚本。首次安装与更新都应检查没有外网请求。GitHub 只用于开发协作，现场启动不访问 GitHub、包仓库或容器注册表。

<a id="section-7"></a>

## 7. 双机、备份和失败时的体验

完整部署规划为单主写入＋备用接管，两台都预装可独立运行的应用、必要业务依赖和匹配版本数据库。PostgreSQL 可采用流复制，但默认异步会存在未复制事务丢失窗口；复制不是备份，也不保证无损切换，见[官方主备说明](https://www.postgresql.org/docs/17/warm-standby.html)。本方案不凭两台服务器就承诺自动无缝切换。

起步方案采用有记录的人工接管：先隔离／确认旧主不再写入，再核对备用数据库与文件副本进度，提升新主、切换内网站点地址、核对租约与交接证据，最后恢复任务。旧主恢复后先作为待重建备用，不自动重新接单。没有隔离依据时保持只读状态，不同时启动两套写入执行器。

数据库外的原产出、接收证据和模型也需要独立备份／副本；备用主机若仍依赖已故障主机上的目录，就不具备独立接管能力。共享素材网盘的可用性另行验证，不能用应用双机掩盖网盘单点。

备份覆盖数据库、不可变文件、配置与密钥的独立受限备份、发布版本和迁移记录。实施起点建议每日可恢复备份，逻辑备份或物理备份＋日志归档必须按下节分别选择；保留期、可接受数据损失时间 RPO、恢复时间 RTO、容量和负责人须在 E13 前明确并实测，本文件不自定现场承诺。定期在隔离目录恢复备份，核对文件摘要及已接收任务，不能只看备份命令成功。

故障体验：网页还能访问但上游失联时显示“状态待确认”并停工作动效；API 断开保留最后画面并标数据中断；服务重启后读回真实任务，不能从 0 开始模拟。备份、恢复脚本与双机配置都属于后续交付内容，目前未创建或执行。

### 7.1 数据库与文件一起恢复

两种备份路线分别验证：只需恢复到每日备份时点时，可使用逻辑导出及相应恢复工具；需要按时间点恢复时，采用 PostgreSQL 支持的物理基础备份与连续 WAL 归档。pg_dump 不能作为 WAL重放的物理基础，依据[官方连续归档说明](https://www.postgresql.org/docs/17/continuous-archiving.html)。禁止直接复制正在写入的数据库目录并把它当成一致备份。

首版优先在约定维护窗口暂停新任务领取及业务文件／交接写入，等待进行中写入落定后，建立同批次数据库备份与其引用文件清单；文件按不可变版本复制，摘要核对通过后才能登记整批备份成功。若改为不停写备份，必须设计与数据库快照一致的文件集合及保留策略并另行验证，不能套用静态目录复制。

备份清单记录 backup_id、数据库备份类型与时间点／LSN（适用时）、schema和应用版本、文件对象及摘要、配置版本、加密／恢复密钥引用。恢复后核对数据库所引用文件齐备，缺失文件对应任务标待核对，不恢复“已交付”工作的自动执行；先恢复只读网站，核对接收事实和旧租约后再开 worker。恢复演练包含缺一个文件、坏一个摘要、缺一段 WAL 和旧 schema 的拒绝场景。

## 8. 交付检查

最终归入 E19 的网站验收包括无缓存断网首开、深浅主题、20／40 频道、来源断线、任务心跳过期、服务和浏览器重启、午夜换日、只读权限、实时数据不使用缓存；方法见[验证计划](../planning/02-前期探索与验证计划.md#13-浏览器大屏e19)。

完整编单离线属于 E07，主备与人工接续属于 E13，目标系统接收证据属于 E12/E19。当前只验证了静态原型及其构造模型，没有安装真实状态服务、创建生产数据库、打包镜像、打通现场网盘或开展真实 Playbox 交接。

### 8.1 无人值守终端与长时间展示

交付终端配置包含开机打开内网地址、浏览器崩溃后的受控重启、维护退出方式、屏幕分辨率／缩放和字体、休眠／锁屏策略、显示器断连恢复以及离线浏览器补丁。只在专用获准终端设置，不能默认修改办公电脑的锁屏或更新策略。

浏览器恢复显示时先确认数据再继续动效；认证或网络失败呈现明确状态。保持单个轮询和动画循环，不因重连反复叠加；候选版本须覆盖跨午夜、连续一个工作周期与超出最长任务的运行，以及多终端同时连接。实际持续时长、观看距离、浏览器版本及最大并发在验收合同固定。当前只有设计要求，尚未执行这些现场测试。
