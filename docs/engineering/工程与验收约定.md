# 工程与验收约定

状态：2026-09-10 引入的工程基线。产品功能、实验步骤和指标仍以[产品需求](../product/01-产品需求文档.md)、[验证计划](../planning/02-前期探索与验证计划.md)为准，本文件不新增业务验收指标。

## 目录与实现

沿用根目录 README 的目录规划。`src/` 放正式实现，`scripts/` 放提取、实验与开发辅助工具，`tests/fixtures/` 只放人工构造或已确认可以公开的微型样例。测试资产不能改名后直接当正式交付。

代码实际形成后按职责分开：业务规则负责素材匹配、时间编排与检查；外部适配负责 EPG、Playbox、大洋、文件来源与模型协议；运行入口负责取单、任务执行和状态展示。不预建空模块、多进程或数据库体系。外部格式变化不应迫使业务规则跟着改写；模型不能跳过确定性检查自行宣告成功。

配置模板入库，密钥、本机配置和现场路径外置。依赖选定后统一声明并固定可复现版本；引入新依赖时说明谁调用、如何安装与如何验证，不能只证明在开发者电脑上可运行。

## 验收怎样认领

工作项引用已有 E 编号及需求章节，只展开本次负责的断言。测试前写“给定什么输入、执行什么动作、应该看到什么”，并明确关键失败行为；不在完成后按实现现状倒填标准。

每次结果至少包含：需求或 E 编号、输入代号及版本、程序与规则版本、测试环境／目标软件版本、执行者、日期、实际观察、通过或失败、证据位置和未验证范围。公开工作项仅保留脱敏摘要，真实材料按本地数据规则留存。

| 实际证据 | 可以说什么 | 仍不能证明什么 |
|---|---|---|
| 文档或文件已经形成 | 已形成待验证产物 | 功能已能用 |
| 本机或 CI 检查通过 | 所列检查覆盖的规则通过 | 目标软件兼容、现场路径可达 |
| 隔离环境内目标客户端验证通过 | 指定版本与样例的读取、内容和保存结果成立 | 正式执行与实际采用 |
| 获准真实流程完成并取得依据 | 本次实际交接、采用或最终文件对比成立 | 未覆盖频道、其他版本或持续稳定性 |

不引入另一套 L 等级或重编 E 编号。用户可见结果用实际客户端或浏览器核验；数值、文件来源与任务状态优先直接回读文件或记录。能由代理稳定完成的步骤由代理完成；必须现场操作或主观判断的步骤，提供“做什么、看到什么算过、异常怎么办”，不让产品负责人代做一般测试。

完整日单、边界用例与恢复验证按本次风险选择。应验证关键拒绝行为：例如缺少必需素材或不支持事件时不可静默交付。测试须能发现真实错误，不能只验证自己预设的结果。候选变化后按影响重验，失败证据保留；不反复重跑直到出现绿色便抹去失败。

## 本机与 CI

当前统一入口：`python3 scripts/check_repository.py`。检查受版本控制的文件是否越过数据边界、文本冲突标记及 Markdown 相对文件链接；本地专有材料链接单独计数，不冒充可在 GitHub 打开。检查不访问业务系统、模型或现场，不读取业务凭据。

GitHub 的“仓库基础检查”调用同一入口；当前通过只说明仓库卫生检查成立，不代表业务测试、PLY 正确性或现场验收。正式代码形成时，在同一工作流加入实际自动测试，再更新本节覆盖范围，不用空测试充数。

提交前把本次文件加入暂存区再运行检查；有未提交产品文档时，另在干净候选上验证一次，避免本地文件掩盖缺失。低风险文档无需完整业务测试；涉及业务行为、外部适配或恢复时增加对应测试，现场验证使用明确授权的副本与环境。
