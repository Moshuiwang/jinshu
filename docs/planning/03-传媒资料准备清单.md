## 3. 素材信息字段：必须把时间说清楚

### 3.1 每个素材文件的信息

| 字段 | 要求 |
|---|---|
| 完整文件名与完整路径 | 保留扩展名和子目录；系统以素材编号引用时，同时导出编号及可取得的文件对应关系 |
| 准确完整时长 | 媒体实际全长，保留原精度；总帧数或精确秒数／时码均可，但须注明单位。不能从文件名整数秒或文件大小猜时长 |
| 帧率／时间基准 | 实际帧率；若按时码表达，保留原值和原格式，注明可取得的计数方式。未知不自行填 25 帧 |
| 版本及可用状态 | 已有版本、语言、季集、可播期、禁用／未就绪等字段原样导出；没有就由规则说明如何判断，不要求手工补造 |
| 文件大小、最后修改时间 | 可从目录导出，辅助区分文件；不代表准确时长或“最新即正确” |
| 信息来源与观察时间 | 来自哪个系统或目录、何时取得、覆盖范围；当前素材与当日日单不一致时注明 |

### 3.2 每次编排使用的信息

同一素材可能多次出现或使用不同区段，以下信息按编单条目关联，不强行放到“一文件一行”的素材表里：

- 原日单行号／条目位置、关联文件或素材编号。
- 整段使用，还是指定区段；若整频道统一整段使用，提供一条适用规则即可，无需逐条填。
- 使用区段的入点、出点及有效播出时长；保留已有精度。说明时间是文件内偏移还是素材内置时码，以及出点是否包含末帧；不清楚时附原界面，由后续受控测试确认。
- 计划开始时间、固定时点和等待／停止等事件；没有固定时点也请说明。

视频全长不等于实际播出时长；修改时间不等于这两种时长。已有 PLY 数值可作对照，但未经确认不能直接当成媒体全长或实际播出时间。

### 3.3 如果系统导不出这些字段

先保留现成导出，不要求手工逐个检查大视频。说明导出缺哪些字段、现场是否允许运行只读工具；项目侧据此准备批量提取办法，在素材所在内网电脑读取，仅交付小型结果表。读取可能占用网盘带宽，使用范围和运行时段应按现场条件确定；不复制原始视频到本项目，不上传视频。

工具可提取媒体信息，不能自动知道人工选择的使用区段和业务规则，这部分仍来自日单或规则说明。缺关键时间信息时可以继续匹配研究，完整时间验收保持未完成。

## 4. 业务规则：一次回答这些问题

每套系统按选定频道回答；不适用写“不使用”，经验做法写明“目前靠经验”，不需要先制定一套新规则。

| 主题 | 需要解释的内容 |
|---|---|
| 输入与素材对应 | 初版用什么名称／编号，对应季、集、语言、分段和文件的方式；名字不一致时怎样找 |
| 版本选择 | FIX、BRC 等标记是什么意思；多个版本如何选；哪些状态不可用；已有可播期如何执行 |
| 包装 | 台标、下条预告、分级提示、导视、赛事包装何时插、插几次、与哪个节目对应；哪些不能随意替换 |
| 填缝与重复 | 可用素材范围、优先级、有效期和重复限制；填不齐或超时怎么办；同一节目是否允许重播 |
| 时间与换日 | 业务时区、一天从何时开始、固定切换点；全长还是区段；帧精度如何处理；超过 24 小时的尾部如何使用及交接 |
| 事件与例外 | 是否有定时、等待、停止、直播或外挂字幕；哪些在此频道使用；提供一条例子或说明不用 |
| 人工修改 | 常见错片、错集、时间调整等如何处理；提供一份已有改前／改后及原因，没有就注明 |
| 最终交接 | 哪一步算审核完成，正式文件放在哪里，之后还会不会修改，怎样判断最终采用的是哪个文件 |

现有日单的 25～30 多小时累计值只用于提出换日问题，不预设它一定是超编、备用或实际连续播出。

## 5. 业务量、模型速度与部署约束

### 本次提供已有业务情况

- 每天大约多少份单，集中在什么时段；最多会同时处理几份。
- 初版通常何时到、最迟何时审核交付；希望系统多久完成一单、单次确认后最多能等多久。没有目标先给当前截止要求。
- 现在整理输入、找素材、选版本、编排、审核、返工各需多久；多人参与记总人工投入，等待另计。估计值不当实测。
- 相关素材目录大致文件数量和容量、更新频率；不要求上传整个库。
- 最终完全断网已是既定要求；如已知，补充可复用设备及可借测条件、部署位置对供电／散热／噪音／网络的限制。未知标待查，不需要现在采购或改环境。

### 这些由项目实验测，不要求用户准备

线上每单 token 用量、请求次数、首响应、生成速度、整单时间、模型能力下限、工具与模型错误区分、API 成本、目标硬件内存和速度、双机报价比较。项目侧先准备候选实验方案；选择付费服务时一次列明服务、数据范围、预算上限和可用接入方式，再确认使用。不得把 API 密钥写进交接文件。

最终速度要求根据业务时限和实际请求量形成，不预先编造 token/s。线上性能不能代替本地硬件实测。
