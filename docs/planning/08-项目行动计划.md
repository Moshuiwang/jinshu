# 项目行动计划

版本：v0.5｜2026-09-10｜按资料、问题与产出推进；不索取联系人名单

本计划帮助产品负责人从当前资料研究推进到试点交付和推广。它不替代[产品需求](../product/01-产品需求文档.md)、[验证计划](02-前期探索与验证计划.md)和[验证台账](07-产品决策与验证台账.md)中的验收条件；进展统一回写验证台账，避免维护两套状态。

## 现在在哪里

产品方向和主要需求已有文档，已收到并读取 Playbox 3 份、大洋 5 份真实日单。尚未完成同一任务的“初版表—素材—最终日单”配套，也没有目标软件中的生成验证和省时实测。

大洋与 Playbox 是两套系统，管理不同频道。按当前范围先完成一个 Playbox 常规录播频道；大洋资料用于研究其频道现状，后续适配另行立项，不作为 Playbox 的输入。

**现在从第 1 步开始。当前最值得做的是找齐一份能解释清楚的完整业务实例，同时确认能否借用现有环境做验证。**

## 一步步推进

2026-09-10 产品负责人明确推进顺序：**线上模型跑通 MVP → 测出模型能力与速度的最低可接受要求 → 硬件实测与预算评估 → 采购 → 本地 LLM 部署 → 离线业务验收 → 试运行与交付。**“能力下限”指本项目任务上的已测可用范围，不等于通用模型排名或某个参数规模必然够用。

| 步骤 | 产品负责人要推动什么 | 项目侧及配合人员做什么 | 本步交付物与进入下一步条件 |
|---|---|---|---|
| 1. 确定试点和完整实例 | 选一份 Playbox 日单，补同日初版表和素材信息 | 对照最终日单，解释包装、版本、时长、换日和人工操作 | 完整业务实例、规则缺口和测试环境说明 |
| 1A. 验证两套系统的导入导出 | 分别提供大洋、Playbox 的版本、导入导出菜单及可取得的导出样本，说明可用测试条件 | 对两套系统各做原单导出、测试副本导入、保存重开及再导出核对；区别节目单与素材信息导出，记录格式、字段保留、路径和失败提示 | 两份能力记录。Playbox 可用输入输出路径是其完整 MVP 通过条件；大洋结果用于其后续适配，不因其暂缺测试条件阻止 Playbox 独立推进 |
| 2. 定义 MVP 与验收标准 | 确认最小可用流程、交单时限、能接受的等待和人工确认负担 | 记录原人工流程；确定正常、疑难及异常样本，约定质量、整单时限、并发与评价方式 | MVP 验收表和人工基线；数值在测试前确定 |
| 3. 用线上模型跑通 MVP | 协调样本解释和目标 Playbox 审核，确认线上验证的资料范围 | 先用能力较强的线上候选跑通初版表、素材匹配、包装与时间编排、异常确认、生成 PLY、校验及人工审核；优先直接生成，必要时验证备选路径 | 目标客户端中内容正确的完整日单、失败清单、人工投入与耗时记录；最小业务闭环成立。只完成最小版本，不提前建设全部交付能力 |
| 4. 找到模型能力与速度的可用下限 | 确认哪些错误不可接受、等待是否可用 | 固定工具、流程和规则，逐档比较线上可调用或托管测试的本地可部署模型；测准确性、工具调用、异常识别、确认负担、token 消耗和速度；失败后区分模型、规则和工具原因 | 模型能力与性能需求表、已测通过／失败候选、部署候选短名单。保留未参与调试的样本验证；无合格本地候选则继续筛选，不凭线上强模型成功直接采购 |
| 5. 将模型需求变成硬件方案和预算 | 协调借测或供应商演示，评审配置、交期、保修与费用 | 用候选实际权重、精度、推理配置及真实日单测目标设备；核对上下文、首响应、生成速度、整单时间、并发、内存余量与单机故障后负载；完成对应交付路径最小断网验证 | 有实测依据的完整双机报价、推荐方案与不足说明。沿用两台主机争取 10 万元、最高 20 万元；不能仅凭“模型装得下”定选 |
| 6. 确认方案并采购 | 批准具体配置、金额、供应商和验收约定，按公司流程下单 | 将模型版本、配置、实测负载与到货验收要求写入采购依据，收到设备后核对配置 | 获批采购方案及到货配置记录；本行动计划不代替具体下单授权 |
| 7. 搭建本地 LLM 与完整业务版本 | 协调部署位置、维护人员与内网条件 | 安装并验证本地模型、Agent、固定工具、规则及素材访问；完善版本可信、独立检查、补料续编、任务恢复、改后复检和双机接管 | 本地可重复使用版本、安装与维护记录；同一业务样本回归通过。量化、推理引擎或工具变化须重新检查，不能继承线上通过结论 |
| 8. 完整离线与人工双轨验收 | 安排真实人员独立审核，对照现有做法 | 在无互联网条件下测全部流程、准确性、token 与整单速度、并发、故障恢复、交接路径和生产文件对比机制；统计确认、审核、返工及维护投入 | 达到事前约定的质量、时限和人工投入要求，E07、E12—E16 等试运行条件全部满足；未达标回到对应步骤修正 |
| 9. 小范围试运行 | 与业务、技术和项目负责人确认范围、周期与退出方式，保持人工审核上传 | 跟踪实际采用、修改原因、等待、维护负担和故障接管 | 约定周期内质量和效率达标，实际采用有证据，失败可及时回到人工流程 |
| 10. 验收交付与推广 | 接收操作、维护、升级及接管安排，组织联合验收 | 整理最终规则、验证结果、已知限制和回退方案；新频道做差异检查 | 首个试点完成交付后决定推广；大洋后续单独适配 |

## 导入导出是 MVP 前置验证

两套系统分别验证，不假定互通。第 1A 步可与样本配套、线上准备并行，但 Playbox 完整 MVP 不能在目标版本的输入输出路径尚未验证时宣称跑通。大洋本轮纳入能力验证，不等于现在建设其完整适配。

需要得到明确答案：能导出哪些节目单和素材信息、哪些格式能重新导入、哪些字段会丢失或被改写、生成文件是否被正确识别、失败时怎样提示。文件能够导出、文件能够导入、导入后内容正确分别记录；菜单存在或取得一份 Excel 不代表双向能力已经通过。

只在独立测试列表或获准测试副本验证，不覆盖正式日单，不触发实际播出；当前无可操作客户端时先收已有导出文件和界面证据，实际导入保持待测。

## 模型能力和速度怎么衡量

模型下限必须同时满足业务正确性、人员确认负担和完成时限。参数量小或单次回答快不单独代表合格。固定的精确计算和文件检查继续由工具负责，模型主要处理理解与歧义；不让模型反复输出整份素材库来制造不必要的 token 消耗。

| 要测什么 | 如何记录 | 对采购有什么用 |
|---|---|---|
| 业务能力 | 错片、错集、漏包装、版本误选、工具调用失败、该询问却未询问，以及人工纠正次数 | 筛出满足本项目质量要求的候选，保留通过与失败证据 |
| 请求规模 | 每单请求次数、输入／输出 token、可取得的推理 token、最大上下文与重试次数；服务未提供的值标为未知 | 确定真实计算量，不能只按文件条目数估算模型负载 |
| 首响应与 token 速度 | 首 token 等待；输出 token 数除以实际生成阶段时间，不含排队及首响应；记录典型值和较慢情形，样本足够时看 P95 | 分别判断读入长资料的等待和持续生成能力；没有分段计时就注明仅为请求平均速度，不冒称纯生成速度 |
| 整单体验 | 模型累计等待、工具耗时、人工确认／审核时间、完整任务耗时和超时情况；分清串行与并行 | 根据交单时限反推模型可用时间预算，以整单是否达标为最终判断 |
| 繁忙与故障场景 | 约定并发下的排队、整单完成时间及另一台关闭后的单机表现 | 确认两台机器各自能独立承接故障后负载 |
| 成本 | 线上每单实际调用费用；双机完整报价、交期、保修和另需确认的部署依赖 | 在合格方案中比较成本，不默认花满预算 |

不预先编造“必须每秒多少 token”。先按第 2 步的业务时限和第 3 步的请求实测形成最低性能要求，再用第 5 步目标硬件端到端验证。线上速度包含服务商设备、排队和网络条件，不能直接推定本地速度；不同模型的 token 切分和推理行为不同，也不能只按 token/s 排名。

若模型质量合格但太慢，先查看不必要请求、上下文、重试和可复用匹配，再比较配置；调整流程后对全部候选重测，不能用变化后的条件直接沿用旧排名。预算内没有同时满足质量与时限的方案时，列出优化或范围调整选项，由产品负责人决定，不静默降低标准。

## 当前第一批行动：一次转交完整清单

直接使用[资料与验证交接清单](03-传媒资料准备清单.md)，这是唯一资料入口，不再分散追问“目录信息”“时间信息”“联系人”。

- 从已收资料中按系统各选一份日单，按清单 M01—M07 收集已有文件和说明；Playbox 用于完整 MVP，大洋用于独立能力验证。
- 每项可以注明没有、不适用或暂不可取得；不复制视频，不逐个手抄时长，不要求另开会议。
- 用户转交后，项目侧检查整个资料包，合并列出剩余缺口及影响，能从文件读取或工具提取的自行处理。
- 清单第 6、7 节提前列出后续测试和采购部署的结果材料，当前尚未产生的不用现在提交。模型指标由实验取得，不让用户猜 token 速度。

资料取得情况统一回写验证台账，再按条件开展线上实验和客户端验证。

## 可以同时进行的工作

补资料期间，项目侧可以继续分析现有样本、整理规则问题；播出技术与工程可以调查现有或借测设备、客户端和断网验证条件。技术实验须有对应测试条件，不把生产环境当实验场。

当前不先采购最终硬件。资料补齐、规则整理、测试条件调查可与线上 MVP 准备并行。最小断网检查使用现有、借测或供应商环境，服务于采购前排除不可交付组合，不要求先建成最终本地系统；最终环境搭建和完整离线验收在采购到货后完成。原验证计划中“工程建设前 E10”的条件在本轮细化为：线上 MVP 可先开展，E10 须在采购定选及完整本地版本建设前通过。

## 如何跟进而不失控

每完成一步，只记录四件事：完成了什么、证据在哪里、还缺什么、下一步交付什么。需要用户配合时，明确具体文件或问题、用途以及缺失会影响哪一步；能从现有资料取得的内容先自行检查，不重复索取。

当前研究与线上 MVP 不要求提供姓名、联系人或责任人名单，也不以此作为开始条件。由用户转交资料或反馈即可；助手不自行联系他人。实际试运行和交付前才确认审核、维护和故障接管安排，其目的是让使用者知道怎样完成工作和获得支持，不为前期研究收集名单。

涉及未确认规则，由频道人员裁定；结果不正确，回到相应步骤修正并复验；条件未具备，继续其他不依赖它的工作。不能用“文件已生成”替代正确性，也不能用“已经放进目录”替代实际采用和播出证明。

本项目当前范围的完成，是首个试点在约定环境中可持续使用、人工总投入下降、审核和维护有人负责、结果可追溯，并完成联合验收；收到样本、写完代码或单次演示成功都不是项目完成。
