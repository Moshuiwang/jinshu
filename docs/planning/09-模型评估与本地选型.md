## 1. 四步路线与每步结论

| 步骤 | 用什么做 | 需要回答什么 | 进入下一步的依据 |
|---|---|---|---|
| A 业务基准 | Codex＋OpenAI 模型；具体模型与配置在运行前固定 | 工作方式能否完成合格编单，整批需要多久，时间花在哪里？ | 先跑代表频道，再跑完整日批次；有结果检查、计时与失败记录，流程性问题已定位 |
| B 可部署候选 API | 首个候选 Qwen3.8-27B，调用可核对版本的云端 API | 换模型后能否理解、匹配、拼接并正确使用工具？ | 与 A 使用相同业务题和标准，记录质量、调用数、返工及速度差异 |
| C 云端自行部署 | 租用获准资源运行目标权重；记录硬件及推理配置 | 脱离托管增强服务后能否维持能力和速度？ | 自部署结果可复现，精度改变后的质量复测；租期、费用与清理条件明确 |
| D 本地选型 | 根据 C 估算候选，再以拟购配置实测 | 哪种本地组合能完成约定日批次，单机故障后是否仍够用？ | 本地性能与差异风险有证据，正式采购前用拟交付配置运行固定评测包 |

A 使用 OpenAI 作为较强能力基准，不预先判定业务全对。其模型不要求成为最终本地候选；B 起的最终候选须可本地部署。一次 API 成功不等于 Codex 中多步业务流程成功。各阶段保持同一业务任务、规则及工具接口；载体、模板或工具实现必须改变时单列变量，避免将差异全部归因于模型。

不先建完整生产 MVP。A 需要能走完代表任务的最小测试工具与检查，缺失工具可在隔离环境补齐；模拟结果标明范围，不当作真实目录性能或 Playbox 验收。现阶段不安装推理服务、不租机、不下载权重；本次产物为文档和执行准备。

## 2. 日批次目标与计时

用户提出每天 **20 多个频道、争取 2 小时内完成**。这是当前评估目标，准确频道数、代表日期、并发和异常比例在实验前固定，不把“20 多”缩成已验收的 20 个。完成终点为编单检查通过并到达约定测试交付位置；人员在 Playbox 的后续审核另记。目标软件尚未验证时，只能报告测试产出完成，不能说现场交付通过。

先测一个代表频道确认记录有效，再测一整天的频道组合，包含复杂任务；合成复制的 20 份简单任务只能测吞吐方法。批次从全部预定输入准备齐并统一发起，到最后一个合格任务完成，排队、重试与失败均计入；另测实际分批到达场景，保留到达与截止时间，不能靠推迟起算隐藏等待。

程序自动记录：

- 每次模型调用的起止、首字、用量及结果；每项工具调用的起止及状态。
- 任务排队、必要人工回答等待、失败重试及返工；从开始到结束的实际总时长保留，人工等待可另列扣除后的辅助口径，不悄悄从“两小时”中删除。
- 每频道合格与否、完成时间；整批实际数量、完成／未完成／超时数量及最后完成时间。平均、P50／P95 和最慢任务一起看，失败任务不从分母删除。

按恰好 20 个频道、全部串行举例，120÷20＝每频道平均 6 分钟；这只是容量预算，不是单频道硬性时限。并发效果必须测，不能乘以任务槽数就声称等比例提速；模型、工具同时运行的区间不能重复相加，批次以实际起止时间及任务依赖为准。

更换模型后的初步预测分别估算模型段、工具段和等待段；仅在调用步骤和次数近似不变时作条件推算，并提供保守区间和依据。模型能力不足可能增加调用与返工，须用 B／C 的实际调用记录修正。不能把 token/s 比例乘到整单总时间，也不能在零实测时承诺性能余量。

## 3. 本地候选与 API 身份

按[行动计划](08-项目行动计划.md)，先完成 A 业务基准，再进行 B／C／D。候选必须有可取得的权重／部署材料和符合实际用途的使用条件，并能形成脱离云端托管服务的部署路径；只提供封闭云 API 的模型不能作为最终候选。首个本地部署候选为 **Qwen3.8-27B**。

2026-09-10 已打开官方 [Qwen3.8-27B 模型卡](https://huggingface.co/Qwen/Qwen3.8-27B)，可查到公开权重与部署说明，故可进入候选评估。仅此不证明其在本项目的能力、速度、目标硬件或 Codex 接入已经通过。其他模型可以后续列入同一评测，但不悄然替换指定的首个候选。

云端可采用能明确权重／配置的托管端点，或在获准云资源上运行目标权重。托管增强版、不同量化版与原权重分别记录；供应方未说明版本、精度、硬件或额外工具时标未知。实际端点、费用、访问与运行条件尚未确定，本轮未发起模型请求或租用资源。若找不到可核对身份的 API，先报告 B 的缺口，再决定是否用 C 替代；不把名称相近或托管增强模型当成同一权重。

## 4. 业务能力评什么

本项目评估的业务能力是能否完成下列业务任务，公开榜单只作背景，不作为本项目结论。

| 科目 | 对应已讨论工作 | 观察与判定依据 |
|---|---|---|
| 业务理解 | 解释 EPG 备注、别名、季／集和版本含义 | 能回指原文和规则，缺信息不补造；无法明确时提出具体问题 |
| 素材匹配 | 从有限候选判断对应素材 | 符合节目与版本依据；明确硬条件不违反；区分无候选和数据未查全 |
| 手册理解 | 识别培训手册的硬约束、经验建议和自由空间 | 不把建议变成强制，也不把必须项当自由发挥；有对应条文或已确认业务解释 |
| 拼接方案 | EPG 主体与适用台标、广告、包装、宣传等组成完整编排建议 | 补充项有依据、主体不漏；允许多个合格组合，不要求复刻人工唯一答案；精确时间由固定计算工具核对 |
| 工具使用与反馈处理 | 提出检索条件、读取工具结果、根据检查失败修订方案 | 调用合适工具、参数正确、理解失败；不把“工具可调用”当“任务已完成” |
| 连续任务表现 | 长上下文、多步和必要人工回答后的继续 | 不漏掉前一步的有效结果、节目条目、版本或已确认选择；有限重试，正确保留未解决项 |

先核对已有 EPG／素材／手册资料，提炼固定用例。起始设计为每科至少正常与边界用例，样本数量、重复次数和通过条件在测试开始前固定并记录；不能为凑数量编造真实业务规则。构造样例仅用于方法验证并明确标识；业务验收样例与调参样例分开，用过来调方案的样例不继续冒充独立验收题。

程序检查可机械判定的必需项；Agent 可辅助整理依据和评价需要业务理解的内容；人员确认程序无法判断的业务争议，并核对评判标准。各自拆成独立任务，候选模型不能作为自己结果的唯一裁判。保留通过／失败／无法判定及各类错误，不把输出流畅或格式正确当作业务正确，也不以平均成绩抵消已知关键错误。

## 5. 首字与生成速度口径

A 阶段先核对 Codex 当前可提供的任务与调用记录；取不到的 token 或流式时刻标为不可得，不从屏幕刷新猜造精确指标。整批和单任务的实际耗时仍可记录，首字与 token/s 只在有可靠观测的调用中报告，并标明测量边界。

测量使用同一客户端的单调时钟计算持续时间，记录到毫秒；另存带时区的开始时间用于溯源。请求、首个有效输出、首个正文输出、末个有效输出和响应结束分别记录。空流事件、角色信息或保活消息不算首字。

| 指标 | 定义与报告方式 |
|---|---|
| 首输出延迟（TTFT） | 从请求发出到收到首个实际模型输出内容的时间；若先输出思考内容须注明，不能把它当成用户已看到答案 |
| 首正文延迟 | 从请求发出到首次出现可供人员阅读的答案正文；直接体现人员等待体验。仅输出工具调用的任务另记首个有效工具请求延迟，不虚构正文首字 |
| 单请求生成速度（token/s） | 优先使用可核验的服务端解码统计；能取得对应 token 数及首末 token 时刻时，按同一口径计算 `(输出 token 数－1)/(末 token 时刻－首 token 时刻)`；不足两个 token 不计算。只有流式文本块时不得把块数当 token 数，无法可靠取得则标估算及方法或不可得 |
| 单请求端到端速度（辅助） | 输出 token 数／完整请求耗时，包含首字等待；与解码 token/s 分开，不能用它混充持续生成速度 |
| 并发整体吞吐（辅助） | 测试窗口总输出 token 数／窗口时长；同时给并发数，不冒充单个工作人员看到的 token/s |
| 业务任务耗时 | 一项业务任务发起至得到可检查结果的总时长，分列模型调用、工具及等待；人工等待单列。不是总验证计划第 6 节真实 EPG 到 Output 的交付耗时 |

token 是模型处理文本的计数单位，不等于汉字数；token/s 表示每秒生成多少个 token。P50 表示一半记录不超过的耗时，P95 表示 95% 记录不超过的耗时，用于观察较慢情况。

token 计数注明模型 tokenizer／服务用量字段及是否含思考、工具调用等内容；分子与计时区间必须对应。隐藏思考 token 或时间不可观测时明确限制，不用答案字数冒充 token 数。不同模型的 token 切分可能不同，除 token/s 外同时对照相同业务任务完成时间。

每组报告实际次数、成功数、失败／超时数、P50／P95 和范围，低样本量的分位数只作观察。冷启动、常驻热状态、缓存命中／不命中，短／长输入、不同输出长度和单请求／约定并发分别记录，不混成一个“模型速度”。云 API 无法控制或确认缓存时明确标未知。

定义参考：[vLLM 官方 Benchmark CLI](https://github.com/vllm-project/vllm/blob/main/docs/benchmarking/cli.md)，已核查其客户端计时、TTFT／TPOT 区分及缓存影响提示。不同工具的同名指标可能定义不同，应记录测量点和公式；本页不要求安装指定评测框架。

## 6. 可复现条件

- 模型：准确名称、权重或服务版本、精度／量化、思考模式及推理设置、tokenizer；可取得时记录权重版本和内容身份。
- 运行：供应方或云主机、GPU 型号／数量、推理引擎版本、上下文与并发、缓存、批处理及采样配置；不可知项显式保留。
- 任务：用例主键与版本、原输入、手册／规则版本、提示／Skill、工具清单与固定返回或隔离实现、允许的迭代条件。
- 结果：原输出、工具调用与返回、计时、token 用量和计数口径、业务评价与依据、全部重试和失败，不只保留成功的一次。

比较候选时复用同一套业务任务与工具，固定或说明模型所需模板差异。量化、引擎、思考模式或提示变化分别成组；云端未知环境的数字不能直接推算本地速度。云端能力初筛后，本地目标组合仍需复测质量、首字、token/s、任务时长及实际负载；“权重装得下”不能当本地方案已经可用。

## 8. Mac 参考配置与采购前证据

用户当前偏好 **Mac Studio Ultra、每台 128GB、两台**，作为参考方案；芯片代际、GPU 核数、SSD、来源、价格与保修未定，不代表采购选型。两台各有 128GB，不能按一台 256GB 估算；沿用故障后每台可独立承担约定负载的要求，不默认把两台分片共同推理当作热备。

云端 NVIDIA GPU 与 Mac 的推理引擎、内存结构和执行方式不同，云端速度只能帮助判断任务规模和筛选配置，不能按显存容量、标称算力或带宽作单一比例承诺。优先争取与拟购 Mac 同代芯片、同 GPU 核数和内存的租测／借测；若云端只有 NVIDIA，C 验证自部署，D 另补 Mac 实测。选择 Mac 推理引擎、转换或量化后，要复测同一业务包的质量、工具调用、首字与整批时间。

容量核对包括模型、运行缓存、长上下文、并发和系统余量；128GB 总内存不等于全部可供模型使用。先测单机能否完成日批次，再评估双机安排和故障后能力；不把两台合计吞吐当成单机接管证据。采购前取得拟交付配置的质量、持续批量耗时、内存峰值和失败记录，按测量波动确定余量；不能用平均成绩掩盖超时。

准确型号核验和历史硬件资料见[硬件调研](../research/06-本地模型硬件与双机热备调研.md)。当前只保留租测可得性、引擎兼容、离线依赖及关键迁移风险等调研问题；安装包、部署脚本和完整运维设计待选型更明确后开展。

## 9. 安全与当前工作边界

权限收紧和危险密钥不可由 Agent 读取是现在就记录的开发约束；具体架构在基本方案确定后落实，见[生产保护与权限密钥边界](../product/04-生产保护与权限密钥边界.md)。本轮只整理文档，不配置权限或读取生产密钥，不开通收费服务；后续实验用获准样本与隔离工具。
