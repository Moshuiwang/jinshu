## 1. 产品定位与目标【已确认】

2026-09-10 产品负责人确定项目名称为“锦书”，拼音及英文标识为 `jinshu`；内部名称为“锦书 · 智能编单系统”；后续大屏访谈确定对外名称为“四达传媒智能编单系统”。公司标识使用 StarTimes 官方 Logo，系统标识按“锦书”的寓意独立创作。

本产品帮助常规录播频道的人员完成素材查找与编排。2026-09-10 产品负责人确定：使用 Codex 作为工作人员的主要工作界面，承载编单任务、必要的业务确认、进度查询和结果领取；配套 Skill（业务操作指南）与 Plugin（打包的技能和工具）提供业务指导与工具。日常整体运行状态由可自动刷新的浏览器页面展示，可放在大屏上。交付包含编单能力、配套工具与规则、状态页及使用维护说明。

原人工流程是拿着打印的节目安排表（EPG），在 Playbox 或大洋中编单，确认后将可执行文件交入指定位置。锦书接替其中的查找和编排：从约定来源自动取得电子 EPG，读取当前素材信息，生成并检查编单文件后放入指定待审核交接目录（Output，不是正式播出目录）。人员导入原系统，检查、必要时修改并确认，然后按原流程执行；不要求改后返回锦书复检或再次批准。锦书事后只读取得最终执行文件，与原产出对比并留存历史，用于后续改进，不介入正式上传或播控。

这是一段较长时期内沿用的产品边界。EPG 来源优先考虑网盘固定目录，具体位置、文件格式和自动取单规则待验证；首期仍先完成 Playbox／PLY，大洋完整适配不因通用流程定义而提前纳入。

当前验证看两项：锦书从收到 EPG 到交付 Output 的耗时，以及原产出与最终执行编单的一致／差异情况。不要求人员填写工时、不计算节省比例；系统记录的人工回答等待只用于诊断，也不以“人工总投入下降”作为本期验收前提。减少人员工作量仍是产品目的，当前由锦书报告自己的运行结果。

当前先准备 Codex＋OpenAI 业务基准；后续阶段见[行动计划](../planning/08-项目行动计划.md)，测试方法见[模型评估](../planning/09-模型评估与本地选型.md)。20 多频道／2 小时是待实测目标，不要求先建完整产品。

## 2. 范围【已确认】

2026-09-10 产品负责人确认：**大洋与 Playbox 是两套系统，分别管理不同频道。**本批大洋 Excel 与 Playbox PLY 分别属于各自系统的频道日单，不是同一任务的输入与输出，也不代表系统间转换流程。沿用本期 Playbox／PLY 优先、大洋后续独立适配的范围。

### 2.1 本期包含

- 从约定来源自动获取 EPG，按明确的频道、业务日期和输入版本建立编单任务；网盘固定目录为优先候选，具体取单规则待验证。
- 持续轮询约定 EPG 输入范围，确认新增、修改及覆盖，保存实际观察到的输入版本。每版保留原始副本、来源、源修改时间、文件大小、毫秒级且带时区的首次完整抓取时间和 SHA-256；最近检查时间独立记录。时间信息用于溯源，内容哈希用于确认字节变化。同频道同日期的不同内容版本分别继续编单，无需先裁定唯一采用版本；产出以文件名或目录名区分版本，互不覆盖。轮询间隔、完整读取与变化识别方式待调研。
- 建立共享的数据库素材索引：首次扫描约定范围，后台增量更新并定期核对，编单读取有明确观察时间和覆盖情况的索引版本，不要求每单重新扫描整个素材库；交付前复核实际引用文件。更新频率、变化接口及扫描成本按目标环境验证。
- 记录素材新增、修改、移动和删除，关联受影响的任务及产出版本；未引用的新素材不影响已有编单，已引用素材变化时未交付任务重新核对，已交付版本保留并提示需复核。是否自动另生成新版尚待讨论，不自动替换正式执行文件。
- 按频道人员确认的规则匹配节目、集数、版本及相关素材，完整编排所需台标、下条预告、分级提示、节目导视和宣传片；具体使用条件与顺序由频道确认。
- 区分文件完整时长与节目单的有效播出时长，按确认的使用区段、必要事件及规则完成时间编排、宣传片填缝和检查。
- 集中处理无法确定的匹配、缺失和时间冲突。
- 生成并独立检查锦书自己的 PLY 产出，保存原始版本并交付约定 Output，供人员导入原系统审核。
- 保留本次任务的输入、规则版本、必要人工选择、检查结果和输出记录。
- 提供浏览器运行状态页，可在大屏展示并自动刷新，让人员看见系统是否在工作、任务到哪一步、是否需要处理问题以及结果在哪里。
- 保护指定 Skill、项目程序、规则与校验组件；每份产出具有独立可核验的运行版本记录，区分指定版本、非指定版本和来源无法证明。
- 锦书对自己交付的文件负责检查；人员在原系统中检查、修改并确认即完成原流程审核，无需返回锦书复检放行。
- 只读取得最终执行文件，关联输入 EPG 和锦书原产出，保存各次取得的版本与差异；区分原样采用、变更后采用、未确认及已知原因，为未来升级积累依据。最终执行身份与读取方式纳入验证，不把普通目录副本自动当作实际采用证明。

### 2.2 本期不包含

- 人工审核后的正式目录上传、生产发布、素材迁移、播控和实际播出。
- 新旧 EPG 的节目条目级自动差异分析，以及对已交付编单／正式执行文件的自动覆盖和补改。EPG 轮询与版本留存、素材索引后台更新及变化影响提示已纳入；生产文件回读与对比按第 12 节执行。
- 飞书自动获取或自动跨网同步。历史 U 盘带入只是原输入方式；现纳入从约定位置自动取得 EPG，不据此扩展跨网同步。
- 外挂字幕制作、转换和关联；第一试点选择不需外挂字幕的常规录播频道。
- 体育直播临场调整、视频内容质检、合规审查和独立版权授权审核。
- 对人工改后的文件再次提供投产批准，或要求人员返回锦书提交复检；后续审核与执行沿用原系统和原流程。
- 大洋完整编单适配实现。本期详细定义 Playbox／PLY；大洋的导入导出能力验证纳入前期探索，完整适配仍作为后续方向。

版权授权由上游负责；本产品必须检查已提供的可播日期、素材版本、时长和编排约束。缺少频道规则规定的必需信息时列为待解决问题，补齐并重检前不可交付；不能凭空推断授权，也不能只靠“忽略”通过。

产品负责人已确认：常规录播覆盖首期主要工作，上述排除项不妨碍启动试点。具体频道、岗位和样本后续补充。

## 3. 人员与责任

| 角色 | 职责 |
|---|---|
| 编单人员 | 在需要时解释 EPG 或处理业务歧义，领取 Output 文件并导入原系统；无需逐单手动发起已具备自动获取条件的任务 |
| 人工审核人员 | 在原系统中查看、必要时修改并确认，按原流程执行；不回锦书复检、不重复批准。确实无法从记录判断的业务差异可集中说明，不要求逐条填写修改原因；可否与编单人员同人为业务待确认事项 |
| 频道业务人员 | 提供当前工作流程、实际规则和样例，裁定业务歧义及人机结果差异 |
| 播出技术负责人 | 确认目标软件版本、EPG 来源与 Output、测试条件及素材访问；配合验证最终执行文件的只读取得方式和实际采用身份 |
| 维护负责人／支持人员 | 处理运行故障、版本更新和规则维护，提供用户可用的接管指引；具体人员待指定 |
| 项目负责人 | 组织需求和探索，联合业务与播出技术负责人决定阶段放行 |
| 工程负责人 | 组织固定工具、格式与路径验证，记录版本、实验、失败和修复证据；具体人员待指定 |
| 版本发布与验收维护人员 | 管理批准版本及独立校验规则、发布和回滚；业务 Agent 无权修改其发布依据、校验记录与凭证；具体人员待指定 |

以上角色说明业务分工，不要求在研究或线上 MVP 阶段提供姓名或联系人名单。当前只请求具体资料、规则解释和验证反馈；试运行与交付前再落实实际审核、维护和接管安排，记录到[决策与验证台账](../planning/07-产品决策与验证台账.md)。技能不得将对话中的“已生成”表述等同于人工审核通过或生产发布。

## 4. 人员工作流程【已确认】

1. 锦书从约定来源自动取得 EPG，保存本次输入版本并建立任务；固定网盘目录为优先候选，具体位置待确认。
2. 系统识别频道、业务日期和节目安排；信息清楚时继续，确有缺失或冲突时才集中请人确认。
3. 系统读取指定范围的素材信息，按已确认规则匹配、编排、填缝并处理可确定内容。
4. 人员处理必要的业务歧义；缺素材等未解决时保留进度，不把不完整结果当作可交付文件。
5. 系统检查自身产出的来源与内容，保存原始版本；通过后将待审核编单文件放入约定 Output，附简洁检查结果。
6. 人员把 Output 文件导入原系统（首期 Playbox），查看、必要时修改并确认，再按原流程保存、交接和执行。该过程承接人工审核，不要求返回锦书复检或批准。
7. 锦书事后以只读方式取得最终执行文件，确认任务归属及实际采用依据，和 EPG、原产出一起保留；自动比较变化，为升级提供历史依据。暂未取得或无法确认来源时标待确认，不阻塞人员原有工作。

人员面对业务说明和必要选项，无需编写复杂提示词、执行命令或理解文件格式。这里的任务是系统的一次编单记录，不包含自动人员派工或新增交接审批。轮询取得完整新版本 EPG 或显式发起新编单时建立独立任务并按各自固定输入继续执行；同一输入的未完成任务可显式继续，见 4.3。已交付任务对应 EPG 的后续新版本也可独立生成带版本标识的编单，不自动覆盖旧产出或替换正式执行文件。

### 4.0 工作入口与流程完整性【已确认，待实现验证】

工作人员以 Codex 为主要工作界面，通过固定任务、Skill／Plugin 与 Agent 协作；本轮不新建替代这一入口的专用业务网页或客户端。大屏继续承担只读展示，Playbox 继续承担原系统人工审核、修改与执行。入口选择已确定，不再把多种 Agent App 的横向比较作为当前前置工作。

Skill 负责指导业务协作，程序负责约束必经步骤。任何必需步骤缺失、失败或无法确认，任务必须保持未完成，不能产生正常交付。明确调用 Skill、固定输出格式、Agent 勾选清单或口头宣称完成，均不能单独证明流程执行完整。

执行任务必须拆到只有一个执行者类别：人、Agent 或程序。需要多方参与的模块应拆成多个任务，以明确输入、输出、完成条件和失败去向连接；Agent 形成查询要求与程序实际查询、Agent 作出选择与程序核对入库分别记录。已确认范围的清单见[执行任务拆解](03-编单动作与交接设计.md)；人员按原有频道分工协作，不新增系统派工或接手审批。

每个必经步骤须有与当前任务、输入及产出版本对应的实际结果；进入下一步和交付时核验前置条件。检查后修改原产出必须重新检查；中断、补料、重复执行和恢复不得丢失仍有效的人工选择、重复交付或静默覆盖结果。业务 Agent 不得通过直接写 Output、改记录或修改检查程序绕过上述约束。具体控制机制及验证方法见验证计划 E21；不承诺每次自动完成或模型判断永远正确。

本次确定工作入口与流程原则；具体插件实现、第三方依赖及接入方式仍须调研验证。最终部署要求按第 9 节执行，不重新打开已确认的界面选择。

### 4.1 典型交互示例【建议基线】

> 助手：已取得频道 A、2026 年 9 月 10 日的 EPG，开始编单。
>
> 助手：第 12 集有两个候选版本，时长分别为……，请确认使用哪个。
>
> 助手：编单已生成并通过检查，文件在 Output。请导入 Playbox 查看，必要时修改，确认后按原流程执行；无需返回锦书批准。
>
> 助手：已取得这次任务的最终执行文件，并与锦书原产出完成对比。变化已按类型整理，原因不明的部分保留待确认。

上述为目标体验，不代表自动读取 EPG、生成、目标系统接入或最终执行文件读取已经实现。

### 4.2 集中处理异常【已采纳】

每条异常显示原 EPG 条目、节目与集数、候选素材及版本／有效时长差异、推荐依据、需要人员做什么，以及对时间编排的影响。人员可以改选、撤回尚未提交的选择；已提交的选择如需更正，保存更正记录并重新检查受影响结果。

- **待解决，不可交付**：缺必需素材或信息、版本歧义、时间冲突、未支持格式或必要事件等。说明怎样补充、由谁确认业务含义，解决并重检后才可继续交付。
- **仅供知悉**：已符合规则的信息说明，不要求人员重复批准，也不得混入未解决问题。

同类原因可以分组呈现，不默认批量接受全部候选。由谁补充事实、所需依据及如何留痕写入频道规则；对话中的临时指令不能替代已确认规则。等待时显示已完成范围、未解决项和下一步，人员无需持续守着对话。

### 4.3 等待补料与继续任务【已采纳】

| 情况 | 人员体验与处理 |
|---|---|
| 同一 EPG 任务缺素材 | 保存已完成内容，显示待补料；人员补齐后显式继续，重读相关素材、检查本次依据有效性并重算受影响编排 |
| 人员退出后返回未完成任务 | 恢复任务进度和已保存选择，显示待处理问题；不要求重新描述整份单子 |
| 已确认素材或条件改变 | 保留仍有效的选择；程序重检受影响结果，Agent 按现有规则重新判断。只有剩余业务歧义才请人确认；旧检查不能代替重检 |
| EPG 换版或人员另发起编单 | 保存版本并新建独立编单任务；同频道同日期不同内容版本各自继续，不因另一版本出现停止旧任务或等待人工选版；不做节目条目级自动差异分析，不静默继承旧版决定；连续观察相同版本不重复建任务，恢复历史内容仍记录新的版本事件；输出文件名或目录名包含版本标识 |
| 已交付后素材或节目安排变化 | 引用素材变化时保留旧产出并提示复核，由人员按原流程处理；EPG 新版可独立编单。不得覆盖已交付或正式执行文件，也不要求改后回锦书复检；最终文件仍事后读取对比 |
| 人员取消 | 停止自动操作，说明已完成与未完成范围，历史记录及已交付结果不被静默覆盖 |

### 4.4 浏览器大屏【展示口径已确认，真实状态待接入】

大屏是相对独立的只读模块，帮助人员查看频道进度、Agent 是否在工作、交接及事后对比状态。它不承担编单操作、人工审批或播控；工作人员仍使用 Codex，人工审核仍在 Playbox。

已确认的展示以工作流和人机交接为主，按播出日期查看今天、明天、后天，默认明天。视觉原型展示 20 个频道，保留扩展至 40 个频道的结构；这与模型评估的“20 多频道／2 小时”目标分别验证。

需求、布局、颜色、动效、状态含义、工程和验收统一由[大屏模块](../dashboard/README.md)维护，本页不重复规定。六个展示阶段为 EPG 接收、素材匹配、智能编排、检查产出、编单员、Playbox 已接收。锦书交付完成以 Output 文件完整交入为准；大屏另显示原系统交接是否完成，Playbox 接收不等于已经播出。最终文件的事后读取与对比不阻塞人员工作。来源失联时标明信息待确认，不把未知显示为成功。不同 EPG 版本各自继续编单，大屏选哪一版展示不影响其他版本执行。

当前只有使用虚构数据的静态演示，真实状态接入待实现。最终页面、资源和状态服务须在局域网独立运行；详细要求见[大屏需求](../dashboard/01-大屏需求.md)与[部署方案](../dashboard/04-内网部署方案.md)。

## 5. 输入输出约定

资料提交统一按[资料与验证交接清单](../planning/03-传媒资料准备清单.md)执行。下文为需求／验证覆盖，不作为另一套逐项索取清单；已收信息先自行提取，剩余缺口合并反馈。

### 5.1 EPG：编单依据与自动获取

本项目统一将业务编单依据称为 EPG。原人工流程使用打印的 EPG；锦书需要自动取得对应的电子文件。这里的 EPG 指上游提供的节目安排。名称不能决定文件格式，具体使用 Excel、PDF 或其他格式须核对样本和频道约定。参考：[DVB 说明](https://dvb.org/solutions/service-discovery-metadata/)、[ETSI EN 300 468](https://www.etsi.org/deliver/etsi_en/300400_300499/300468/01.19.01_60/en_300468v011901p.pdf)。

优先探索从网盘固定目录自动取得 EPG。来源位置、支持的文件形式、如何识别频道／日期／输入版本以及何时视为文件准备完成，纳入 E18 验证；当前未确定真实路径，不配置监控或声称已自动取单。人员无需为每份可正常识别的 EPG 再手动提交一次。

系统保留实际取得的 EPG 及原条目位置，匹配和异常可回指输入；名称与计划时长不保证和素材一一对应。若样本为 Excel，再核对工作表、合并单元格、隐藏行、公式值及跨日表示等解析事项；不支持的格式明确说明，不静默漏条目。

2026-09-10 已收到的大洋 Excel 属于其所管频道的日单资料，含播出时间、节目名、时长三列；是否就是编单依据 EPG 仍待确认，不能替代 Playbox 同日 EPG。现有日单也不因本次术语统一而被重新认定为 EPG。

完整 MVP 的素材信息仍须支持准确全长、实际帧率及使用区段／有效时长核对；计划开始时间、固定时点与换日属于编排信息。资料字段与缺项处理见资料清单，不复制或上传原始视频。

### 5.2 网盘素材信息

视频文件位于封闭局域网的网盘。系统只读扫描指定范围，取得编单需要的信息；本期不修改、删除或重命名原素材。

素材信息快照记录扫描时间、来源范围、文件身份信息及读取结果。快照是本次观察记录，不代表复制或冻结视频文件本体。读取失败、文件仍在写入、身份或时长无法可靠确定时，应列为异常。

扫描范围和并发按现场规模验证；分别记录扫描、取得时长所需时间及对现有工作的影响。使用缓存时须在本次任务中确认有效性，不用旧缓存代替当前信息。界面应说明扫描进度、不可读取范围与待处理原因。

### 5.3 PLY 与附带记录

- 主输出：目标 Playbox 版本能够正确读取的 PLY，存入约定业务 Output，供人员导入审核。业务 Output 具体位置待确认，不将项目本地 outputs/ 默认视为现场交接或正式执行目录。
- 版本标识：每次生成的文件通过文件名或目录名明确包含版本号，并关联输入 EPG 版本及任务。同频道同日期的多个版本分别保留、不覆盖；同一输入显式重做的产出也须有独立标识。具体命名或目录方式后续确定。
- 检查报告：输入来源、素材扫描时间、条目对应、使用区段与有效时长、必要事件、时间检查、填缝内容、异常处理、对应输出版本和检查时间。报告明确只适用于该输出与本次观察到的素材状态。
- 任务记录：本次规则和工具版本、模型配置、人员确认和最终校验结论。
- 产出来源与采用记录：输入 EPG、批准版本及实际执行内容依据、锦书原产出及其检查记录、最终执行文件的来源和取得时间、自动差异及已知原因。人工审核由原流程承接，不另建回锦书批准的步骤，详见第 12 节。

PLY 内实际保存哪些字段、使用何种编码及路径规则，须以样本和兼容性验证确定。不能把推测字段写成既定格式。

生成端路径、人工审核端路径与下游约定路径须建立明确对应。试运行前，在隔离测试环境或由播出技术负责人执行的只读检查中，验证相同 PLY 的素材可访问且身份一致。生成电脑可读或客户端能打开文件不能单独证明交接环境可用。

## 6. 编单规则

产品负责人进一步明确：EPG 给出主体节目安排，不含台标、广告等完整播出所需内容。编单需要依据新人培训手册等业务规则，把主体节目与适用的包装、广告、宣传等内容拼接起来；实际规则包含必须遵守的约束，也有较大的自主编排空间。具体必加内容、位置、次数、可选素材及自由选择范围以手册和业务说明为准，不能由 EPG 缺行推断“不需要”。

因此素材匹配完成只得到主体节目的对应关系，后续还需形成完整拼接方案。Agent 在规则允许范围内作编排选择，程序分别负责素材检索、精确时间计算、明确约束检查及结果保存；每个执行任务仍须只有人、Agent 或程序中的一个执行者。多个合格方案可以成立，不要求与人工成品唯一一致，也不因存在自由选择就逐处请人批准。业务规则缺失或冲突时才交人明确。

数据库须区分源 EPG 条目与编排新增条目，新增内容关联所用素材、规则依据和编排方案；不能伪装成原 EPG 已提供的条目。检查既要验证主体节目未漏，也要验证应补内容及拼接约束，不能简单要求最终编单与 EPG 逐行一一相同。

| 规则 | 要求与状态 |
|---|---|
| 素材匹配 | Agent 主导理解 EPG 与素材的业务对应，调用固定工具检索并比较候选；依据充分且明确条件检查通过时自动选择，剩余业务歧义由人员确认；保存选择及依据【已确认】 |
| 版本选择 | FIX、BRC、上传时间等是会议中的现状线索；具体优先级、例外和可用状态须写入频道规则并确认 |
| 时长与时间 | 分别记录文件完整时长及已确认使用区段的有效播出时长；无区段信息时须先确认是否整段使用，不能默认二者相等；帧率、取整、剪入／剪出点及分段边界由样本验证 |
| 必要事件 | 由试点确认等待、停止、定时及其他非视频事件是否存在；使用的事件必须被正确表达和校验，未支持时明确阻止交付，不静默忽略 |
| 填缝 | 只使用指定且在有效期内的宣传片，遵守频道规则；不能填齐时异常，不自行裁剪正片【已确认】 |
| 定时与跨日 | 按频道确认播出日、时区、起止点与换日交接规则；审核显示跨日部分及超出目标时段的内容。真实样本有非零点起单、条目累计超过 24 小时的情况，不能据此自动截尾或判错；尾部是否超编及如何处理待现场确认 |
| 节目包装 | 按频道规则检查台标、下条预告、分级提示、节目导视等与正片的对应关系及顺序，不能把它们一律当作可替换的填缝片；具体插入条件、次数和例外待确认 |
| 重复播放 | 同一素材允许按规则出现在多个位置，不按文件名去重；已确定的匹配可复用，各次播放的顺序、使用时长及可播约束分别检查，减少无意义的重复确认 |
| 版权与可播期 | 上游负责授权；检查提供的可播日期等约束，缺少频道规则规定的必需信息时列为待解决，补齐重检前不可交付【已确认／审核细化】 |
| 覆盖不足 | 先完成能确定的部分，问题集中处理；无规则支撑的决定不能静默通过【已确认】 |

名称中的时长仅作为匹配线索；时间编排以经确认的准确时长与使用区段为准，保留帧精度。连续日期的集数、重播和包装差异可用于研究频道规则，不从样本自行推导每天递增或固定重复次数。

本轮样本与检查依据见[真实日单首轮检查](../../data/production/2026-09-10_全天编单/首轮检查.md)。上述要求不代表已验证具体频道规则或客户端兼容性。

填缝可能存在多个合格组合，评判依据是业务规则与编排效果，不要求与人工逐字节一致。

上述时间及事件要求用于准确表达既定编排，不增加自动裁剪正片或视频编辑功能。第一频道如不使用某类事件或区段，应明确支持边界并保留不支持时的识别检查。

整段使用的条件可以由已确认的频道规则统一指定；符合条件的条目无需逐条询问。规则不足以确定使用范围时才集中请人确认。

## 7. 工程控制要求

以下为需求方向已确认、具体实现和验收阈值待设计的工程基线。

### 7.1 生成、检查与反馈

Agent 主导 EPG 与素材的业务匹配，理解节目身份、别名、季／集和版本等对应关系，调用固定工具检索候选并保留选择依据；依据充分且明确条件核对通过时可自动选择，不能消除的业务歧义交人确认。素材存在性、必需属性与明确限制的核对，以及精确计算、文件生成由经过测试、固定版本的工具执行。模型信心不是选择依据，程序检查完整也不能单独证明语义匹配正确。规则已可靠确定的简单对应关系可以复用，无需逐条重复推理或请人重复确认。技能调用稳定工具，不在每次业务任务中临时修改程序或放宽规则。

检查须覆盖输入条目是否完整、素材对应、版本、使用区段、有效时长、必要事件、路径、播出模式和时间安排。生成后回读 PLY，并与预期编单核对。开发和验收阶段须通过目标 Playbox 实际读取验证；试运行前完成 5.3 所述交接环境检查。业务运行时哪些检查自动执行、哪些由人工在 Playbox 完成，须在探索后明确。

### 7.2 状态与异常

业务状态至少涵盖：待确认输入、扫描中、编排中、待处理异常／待补料、生成校验中、正在恢复、待人工审核、失败／已取消。具体显示形式由载体体验验证确定；状态由用户输入和工具结果共同决定，不能只凭模型文字宣称成功。

失败时停止后续写入，保留已完成的匹配、编排及原因，说明已完成和未完成范围。直接生成路径不得把未完成文件混入正式交付位置；Computer Use 路径应停止自动操作并标明客户端进度，支持人工接管。人员可显式取消任务。

源目录的 EPG 出现新内容版本时，新旧任务分别使用各自固定输入继续执行；不因此使旧任务检查失效。若本任务已固定的输入副本被改动，或其已引用素材／检查依据发生变化，则阻止以失效检查结果交付并提示重新检查。素材索引后台更新持续记录变化；已交付编单的引用素材变化时保留原交付事实并提示需复核，不静默覆盖输出或正式执行文件。生产文件回读与对比按第 12 节执行。

### 7.3 记录与权限

使用数据库管理编单任务、EPG 输入版本及逐条节目要求，分别建立独立唯一主键并保留关联；工程设计沿用 UUID。条目保留原文位置及备注，匹配、选择、编排和检查通过主键关联。相同输入及解析版本的重复解析不重复插入，重复播出条目分别保留；新版本不覆盖旧记录。原始 EPG 字节仍以独立副本保存，由数据库关联其来源、毫秒级接收时间和 SHA-256。数据库编号由锦书生成，不增加传媒填报要求。

每次任务有独立输入与输出记录；系统自动保存来源、已确认编排、版本、检查和差异。同一已确认编排在固定生成器版本下应能复现输出；模型重新推断不保证相同，因此保留最终选择。素材与最终执行文件只读，业务 Agent 仅写任务工作区，正常 Output 由受控交付程序写入；发布副本与独立检查记录受保护。具体来源与历史边界统一见第 12 节，不要求人员另外维护一份表。

## 8. 实现路径：已确认主线与新增调研候选

| 路径 | 方式 | 决策依据 |
|---|---|---|
| 优先直接生成 | 解读 PLY，技能调用固定工具生成并校验 | 结构和业务语义可可靠掌握，目标 Playbox 读取及内容验证通过 |
| 其次验证批量导入 | 生成目标版本支持的 CSV／文本，经 ListBox 导入并保存 PLY | 早期核对菜单与授权；字段、有效时长、事件、路径和导入错误处理经过验证 |
| 必要时 Computer Use | 选定 Agent 通过已验证的电脑操作工具操作 Windows 上的 Playbox，插入素材、调整并保存 PLY | 直接生成与批量导入未满足要求，且目标环境操作能力得到实证验证 |

路径由工程探索决定并版本化，不让 Agent 在业务任务中随意切换。需要客户端的路径可能使用专用 Windows 编单电脑，其软件授权、操作隔离和接管条件待验证。三类候选路径最终均交付待审核 PLY（图形操作再分 Windows 直接操作与 Mac 远程操作），当前没有任何一条通过现场验收。

2026-09-08 调研补充：官方资料显示部分 ListBox Neo 版本支持 CSV／文本批量导入，可作为直接生成与逐条界面操作之间的候选方式。Computer Use 也可探索 Windows 原生操作与 Mac 经内网浏览器远程桌面操作两种部署方式。以上均未在目标设备验证，不改变本期输入输出或生产边界，详见[调研记录](../research/04-PlayBox与Codex操作路径调研.md)。

## 9. 模型与部署【已确认】

最终在不能连接互联网的内部局域网运行，工作人员以 Codex 为主要界面，本地模型与业务执行组件的具体接入组合按部署阶段验证，状态页也须在内网正常刷新。[载体调研](../research/05-Agent载体候选调研.md)保留历史比较依据，模型与配置实测方法见[验证计划](../planning/02-前期探索与验证计划.md)。

基本方案明确后再展开两层安全：局域网独立运行，以及防止 AI 越过护栏对生产造成不可逆破坏。具体依赖、权限、执行约束及验证机制在该专题复核；不以完整安全实现作为云端模型评估前提。E10 最小断网仍须在采购定选与完整本地建设前通过，采购部署后再完成完整离线和使用验收。线上输入限于获准的 EPG、素材信息及必要编单内容，不发送完整视频；截图路线使用前确认实际截图范围。

用户当前参考为 Mac Studio Ultra 128GB 两台，具体代际与配置待核对，不作为性能或采购承诺。安装部署目前仅做必要调研，完整实现待方案明确后开展。

安全优先防止 AI 越权、人员误指令或借 AI 开发／运维能力破坏生产；危险密钥不能放在 Agent 可读取的明文或可间接提取的环境中，受控执行组件仍须限制动作和目标。权限、语言／指令处理及密钥约束统一见[生产保护与权限密钥边界](04-生产保护与权限密钥边界.md)，详细机制尚未落地。

### 9.1 双机与恢复

两台模型主机争取合计 10 万元以内，最高 20 万元；各自能承担故障后负载，预加载模型、自动切换，保留已确认进度、不重复交付。具体配置和实际负载须先验证，Mac Studio 是候选而非定选；配套设施与费用口径见[硬件调研](../research/06-本地模型硬件与双机热备调研.md)。

故障时页面或任务入口显示“正在恢复”及已交付文件位置；超过约定等待时间，说明怎样交回原人工流程并获得支持。恢复时限在试运行前确定；模型双机不等于网盘、客户端、加密狗及整条链路都有冗余。

## 10. 阶段与验收

先用一个常规无外挂字幕的 Playbox 频道验证，再进行 1—2 个频道试运行和逐步推广。阶段顺序由行动计划统一说明，通过条件见验证计划第 7 节，当前是否已完成只记在台账。

验收看锦书生成内容是否满足频道规则、收到输入到 Output 的耗时是否可用，以及最终执行单的一致／差异记录是否可靠；浏览器大屏、离线运行和故障接管也是交付项。发现关键错误须解决并复验，不能以平均一致率替代检查。当前不以人工节省率或人工计时基线作为放行条件。

## 12. 运行版本可信与生产采用追溯【新增需求已确认，实现基线待验证】

### 12.1 每次任务都能回答三个问题

1. 这次取得的 EPG 是哪份，锦书使用了哪个指定版本完成编单？
2. 锦书交入 Output 的原始文件是什么，本身的来源与内容检查是否通过？
3. 人员最终实际执行哪份文件，相对锦书原产出变了什么，哪些原因已经确认？

锦书负责自身产出的检查；人员在原系统中检查、修改并确认，按原流程执行。最终文件对比是事后分析，不是回锦书重新审批，不阻塞原流程。软件加载与实际播出的证据分别记录，不互相冒充。

### 12.2 优先防改，同时提供可信来源记录

设计优先采用受保护的发布副本：业务运行账号只读 Skill、项目程序、工具、规则、依赖和运行配置；草稿与工作文件放在独立可写区域。发布、升级和回滚由维护权限执行，单个任务固定使用一份已批准版本；工作期间升级不让同一任务悄然混用新旧版本。

每个发布版本有完整内容清单和内容指纹，覆盖影响运行的 Skill／提示与配置、程序和工具、业务规则、必要依赖、Agent 与模型配置；本地模型权重记录相应内容身份。保留实际输入、人员选择和工具执行事件。版本名称和 Git 提交号只作索引，不能替代实际执行内容证明；同版本模型也不保证每次推断相同。

实际加载／执行的副本和产出身份由业务 Agent 无权改写的执行或记录组件绑定并存档。仅在开始和结束各算一次指纹，不能排除“中途修改、使用后恢复原样”；必须用任务固定的不可变副本，或能覆盖实际执行步骤的独立取证机制。校验组件、批准清单、证据存储及签名／凭证材料不得由被校验 Agent 自己控制。单纯把一个版本号写进日志，不构成可信证明。

如果暂时无法阻止 Agent 修改开发目录，允许保留修改用于调查，但产出必须按实际证据标记：

| 来源状态 | 判断依据 | 正常流程处理 |
|---|---|---|
| 指定版本，来源已核验 | 实际执行副本与批准内容一致，证据完整，产出绑定对应运行 | 继续独立内容检查，通过后交付 Output，由人员在原系统审核 |
| 非指定版本 | 已证明使用了未经批准或已变更的内容；记录实际指纹、变更项与阶段 | 隔离并交维护人员处理，不给标准交付结论 |
| 无法证明／混合版本 | 缺证据、执行期间内容不可确定，或步骤混用了不同版本 | 明确标记，不猜测“应该是指定版”；阻止作为锦书正常交付进入 Output |

非指定版本的结果即使内容检查通过，也不得伪装为标准版本产出。正常处理是以批准版本重新生成并检查后再交付 Output；不由锦书为人员在原系统中的改后文件签发投产许可。变更发生在某份产出之后，不追溯篡改此前已取得可靠来源证据的产出状态。

### 12.3 独立检查针对锦书原产出

生成器可做自检，正式检查由独立、受保护的组件执行。依据输入 EPG、已确认编排、素材观察记录及批准规则，重新读取锦书生成的文件，核对完整性、片目／版本、顺序、有效时长、必要事件、时间冲突、可播约束和约定环境路径。目标软件兼容性验证保留。

系统自动记录原产出的内容身份、任务／频道／日期、检查器和规则版本、检查时间、范围及结论。锦书在交付前更改或重新生成文件时，应重新检查；旧检查不能用于新的锦书产出。来源可靠且内容检查通过，才作为正常结果交付 Output，并标为待人员在原系统审核。

人员导入后查看、修改并确认，沿用原流程执行，不要求将改后文件返回锦书，不在锦书中另做审核绑定或投产放行。锦书原检查不证明改后文件正确，最终审核责任由人员及原流程承接。事后对比发现差异用于分析和改进，不自动撤回、删除或替换执行文件。

### 12.4 保留 EPG、原产出与最终执行文件

按任务、频道、业务日期和输入版本关联三类核心材料：本次取得的 **EPG**、**A 锦书原始产出**、**C 最终执行文件**。沿用 A／C 是为避免混淆历史记录；原方案的 B 人工审核中间文件不再是必交材料，有现成中间版本可辅助解释，但不能要求人员额外提交。

EPG 与 A 保存取得／生成时的内容；C 在实际取得后保存来源位置、时间、内容身份和采用依据。后续发现新的实际执行版本时另存记录，不覆盖旧文件；同名或修改时间相同不能证明内容相同，也不能仅凭文件名把不同任务关联。

需要验证能否通过约定位置或原系统已有的导出方式，只读取得完整、稳定的最终执行编单；固定目录只是可能路径。还须验证怎样确认这份文件确被系统加载或实际采用，而不只是出现在目录里。目录读取、系统实际采用和实际播出分别记录；只有相应证据时才作相应结论。

最终执行文件尚未取得、内容仍在变化或实际采用身份未确认时，保留待回读／待确认。能力当前未验证，列入 E16；不能把待验证项写成已经可以读取。测试先用隔离样例验证机制，真实任务发生后再积累实际记录。回读失败不阻塞人员按原流程执行，由项目侧处理记录缺口，不要求日常审核人返回锦书补一次批准。

### 12.5 对比结果与升级依据

系统自动对比 A 与 C，同时保留 EPG 作为原安排依据。文件级对比说明是否原样采用；业务对比说明节目、素材版本、顺序、区段、时长、包装、填缝或事件发生了什么变化。原系统保存导致的编号、编码或路径规范化，只有经过目标格式验证才归为非业务变化；未知关键变化保留待确认。

| 采用状态 | 所需依据 |
|---|---|
| 原样采用 | C 的实际采用身份已经确认，且与 A 内容相同 |
| 变更后采用 | C 的实际采用身份已经确认，且与 A 不同；展示业务变化与已知原因 |
| 明确未采用 | 有业务撤回、作废或拒收等明确记录 |
| 待确认 | 未取得最终文件、只有目录副本、任务归属或实际采用身份尚未确认 |

差异不直接等于锦书错误。已确认的原因可包括锦书匹配／编排错误、EPG 后续调整、素材更新、人员选择另一种合格编排、软件保存变化等；原因不清楚就保持未知，不让模型猜成事实。事后取得的新 EPG 可作为变更依据另存，不替换原任务输入，也不扩展为自动改单。

自动保留原值、新值、影响条目、相关输入与运行版本、最终文件来源和已知原因；同类问题集中整理，需要时再核对业务含义，不要求人员逐条填修改记录。真正需要修复的事项形成升级候选和回归样本，不能仅因文件有差异就判原产出错误。

按版本分析产出与最终执行文件的一致／差异、已确认问题类型，并保留未取得最终文件等未知项；一致率不直接命名为正确率，具体分母和未知项处理以验证计划第 6 节为准。经过事实核对的修正用于后续版本改进和验证；不自动把生产变化写回正在运行的 Skill、规则或程序。历史记录的用途是帮助升级，不是另建一套人工审批流程。
