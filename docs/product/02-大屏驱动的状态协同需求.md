# 大屏驱动的状态协同需求

版本：v1.1｜2026-09-10｜联网开发核查后完善的功能设计，尚未完成真实接入。属于[产品需求 4.4](01-产品需求文档.md#44-浏览器大屏展示口径已确认真实状态待接入)的专项展开，不替代完整编单需求。

## 1. 本次要形成的能力

让一张频道日单从收到 EPG 到 Playbox 接收的过程有真实、连续、可追溯的状态，大屏自动反映进度、人工交接与异常。页面外观已经实现；还需要任务登记、运行事件、人工与目标系统证据、状态保存和内网供数。建设这些能力不自动实现素材匹配、编排算法或 PLY 兼容性，也不授权自动操作正式播控。

| 大屏要回答的问题 | 必需的后台能力 | 当前情况 |
|---|---|---|
| 哪个频道、哪天播出的单 | 频道名录、每日计划、EPG 版本与任务关联 | 演示模型已有；真实名录与计划待接入 |
| 现在走到哪里、之前怎样 | 节点事件、尝试次数、状态转换、历史保存 | 六态原型已有；持久化未实现 |
| Agent 是否真的在干活 | 当前执行归属、开始／结束事件、任务心跳与过期判断 | 演示 running 驱动；真实执行证据未实现 |
| 哪些到了编单员、哪些已完成 | Output 交付、人工接手／完成事实、Playbox 接收事实 | 只有模拟事件；实际获取方式待验证 |
| 哪些需要关注 | 故障／回退、缺资料、待确认、时限计算与去重汇总 | 原型有部分提示；真实判定待实现 |
| 断网、刷新、重启后是否可信 | 数据库、完整快照、服务端时间、断线及恢复 | 浏览器演示无持久化 |
| 最终执行单与原产出情况 | 文件身份、采用证据与事后对比 | 演示计数；真实机制待验证 |

主视觉不增加业务操作。已有主题、动效、日期轮播控制只服务展示设置。

## 2. 频道日单、版本与日期

**展示单位是频道 × 播出日期；执行单位是该日单的一次输入／编单版本。**首批 20 个频道来自配置，未来扩到 40 不改表结构。展示编号固定，不能因故障排序或换名而变化；真实频道不能沿用虚构名称。

每天先按已确认的频道范围形成计划，即使 EPG 没到也有对应灰色槽位。默认试点频道每天有全天单；停播或无需编单必须有明确计划依据，不能因缺 EPG 自动减少分母。“尚无任务”与“数据未取得”不同：来源正常、计划存在且没有输入才算 EPG 未到；来源断开时显示待确认。

同一文件再次出现按频道、播出日期、内容摘要和来源规则去重。EPG 换版或显式另发起编单建立独立任务，保留旧版本；新旧版本不自动对比、不静默继承选择。日单记录有一个明确的当前展示任务，切换需要登记选择依据；有两个不能裁定的新版本时标“版本待确认”，不得按最后修改时间猜。旧任务已接收不使新选任务自动完成，旧完成记录仍保留。

2026-09-10 后续逐项决定补充：EPG 文件级变化通过轮询与哈希核对留存版本，不做节目条目级自动差异分析；同频道同日期的不同完整输入版本各自继续编单、输出带版本。上段的“当前展示任务／版本待确认”仅指大屏投影，不能作为停止其他版本或等待人工选版才能执行的条件。多版本在大屏如何选择展示仍待专项细化，不由本轮任务拆解擅自改动既定外观。

工作日期仅作记录，今天／明天／后天均指播出日期。以部署时确认的业务时区计算，演示为 Asia/Shanghai；数据库保存带时区时间。全天播出区间为该日 00:00 至次日 00:00，交付截止为播出开始前至少 24 小时。例如 9 月 12 日全天单，要求 9 月 11 日 00:00 前确认接收。截止值连同当时的规则版本固定在日单记录，不因修改默认配置而改写历史。

跨午夜只改变展示日期窗口，不能重建或清空已有任务。超过窗口的未完成任务保留，并在辅助提示中给出遗留数量；汇总页本次仍不建设。

## 3. 每个节点凭什么亮起

| 节点 | 进入／正在做的依据 | 正确通过的依据 | 缺证据时 |
|---|---|---|---|
| EPG 接收 | 输入采集器确认完整读取并开始解析 | 频道、日期、版本识别通过，进入匹配 | 未收到为灰色；文件不完整或身份不明为问题 |
| 素材匹配 | 匹配执行实例领取任务并开始，任务心跳有效 | 必需素材及选择依据齐全，进入编排 | 等待补料时停止工作动效、显示原因 |
| 智能编排 | 编排实例开始处理且心跳有效 | 形成候选编单并进入独立检查 | 未生成、校验未过不能跨到人工 |
| 检查产出 | 检查实例开始且心跳有效 | 来源与内容检查通过，原产出已可靠保存并交入 Output | 生成文件存在不足以证明通过或交付 |
| 编单员 | Output 已交付计“待接手”；原系统的可靠接手事实计“处理中” | 有人工完成并交给原流程的事实 | 无信号显示“待确认”，不能靠停留时长推断 |
| Playbox 已接收 | 原流程交接后进入待接收状态 | 目标节点已接受指定文件并开始后续工作，有对应接收证据 | 仅复制文件／上传服务器仍待确认；不显示已完成 |

人工信号优先从现有原系统记录或可核实操作记录取得，不新增返回锦书审核按钮。如无法可靠取得“接手／完成”，允许人工阶段暂时未知；在真实展示前通过 E12/E19 确定来源。后续若确需新增人工登记入口，单独明确体验，不能藏在这次大屏后台设计中。

Playbox 接收是展示交付终点，表示待执行，不表示已播出。是否提供可靠接口、日志或其他只读证据仍待现场验证；不能假设 Playbox 已有某个 API。后续拿到强接收证据时可以确认交付，但仍不凭空补造人工接手时间。

## 4. 状态、历史与动效

槽位六态及颜色只由[设计基线](../design/大屏设计基线.md)定义。真实状态再带一个“信息是否可信”的属性，不把业务失败、运行等待和信息中断混在一起。

- 每份当前任务最多一个处理位置。节点尝试与结果可多次发生，历史不覆盖；失败重试需明确恢复事件。
- 等待排队、补料、业务确认或人工接手时保留最后位置，停止该任务的工作动效，用节点下方简短文字说明等待数量；只有真正开始处理才微闪。
- 错误返回上一节点后，原故障槽位保留红圈灰心。回退事件本身不是执行证据；重新领取并开始后，上一节点的 Agent 才可微闪。
- 正确或告警通过后保留历史圈与淡绿色静态线；运行段及光点用频道色；故障和回退线为红色。信息过期时冻结流动，不擦除最后已知结果。
- Agent 图标微闪条件：至少一个归属该职责的执行尝试为 running，且其任务心跳仍有效、数据源可用。服务进程在线、队列有任务、定时器跳动都不足以触发。共享 Agent 某任务失败时，其他正常工作可以继续让图标微闪。
- 原型每 8 秒推进状态的定时器仅限演示模式。真实模式只能由真实事件推进，不得在接口失败后切换为假数据。

实施起始参数建议：任务心跳 5 秒，超过 20 秒未更新标“状态待确认”；网页每 5 秒取得快照，超过 20 秒没有成功取得快照标“数据中断”。这是待 E19 实测的可配置起点，不是现场已承诺的实时性指标。快照成功返回也不能掩盖上游采集器或执行任务已失联。

网页从后台标签、休眠或断网恢复时，先显示“重新确认状态”，取得新快照后才恢复工作动效；不能让停留的旧画面装作实时。观察信号失效只改变可信度，不删除已经证实的完成／故障历史。设备时间明显不准时提示维护，截止与交付仍按服务端业务时间判断。

“暂停动效”只停止光点与闪烁，“停留本日”只停止日期轮播，两者都不冻结真实任务记录或最近更新时间。减少动态偏好在真实版本同时关闭非必要动画和自动轮播；如果因阅读需要保留某一时刻画面，必须标注静态快照时间，不能与实时画面混淆，相关模式本轮不另行增加。

## 5. 统计与需关注事项

| 显示 | 口径 |
|---|---|
| 完成 x / y | y 为当前播出日明确需要编单的首批频道日单数；x 为其当前展示任务有有效 Playbox 接收证据的数量；无输入仍进入 y |
| 超过交付时限 | 当前时间达到截止且未确认接收；已晚交并最终接收后不再算“未交超时”，保留晚交事实 |
| 故障／回退 | 按日单去重，同一任务多条问题不重复算成多份单；故障与超时可同时存在，不能相加当任务总数 |
| 编单员待接手 | 已交付 Output，尚未取得人工接手；数据源不可靠时另外标待确认 |
| 编单员处理中 | 可靠接手事实存在，未完成；不要求人工心跳，不用“Agent 工作中”解释人工状态 |
| Agent 处理中 | 对应节点当前可信 running 尝试数；不混入等待、回退途中和失联 |
| 最终文件反馈 | 有资格回读、待回读、对比中、已对比／失败分别计数；未知不当无差异，差异不直接当编单错误 |
| 系统耗时 | 完整 EPG 收到至成功交付 Output，含等待和重试；不混入人工处理及 Playbox 等待 |

上方优先显示故障、截止问题、来源中断和版本待确认的短摘要，详细条目留在持久记录及后续工作界面。过去的未完成日单仅以辅助计数提醒，不在三日主图中混放。

## 6. 内网与数据使用边界

首次打开、刷新、服务重启、字体与图标加载都必须在断开互联网的局域网完成。大屏从本地服务读数据，不直接访问模型、数据库、网盘或 Playbox；不依赖 Sites、云数据库、CDN、外网登录、在线授权验证或遥测。

后台只输出编号、日期、状态、汇总、版本和简短脱敏原因，不把人员姓名、素材完整路径、业务文件或密钥交给大屏。原文件在内网文件存储中留存，数据库保存关联及证据索引。运行网络、访问范围与来源账号通过现场配置落实，不能因为在内网就让任意浏览器提交成功事件。

## 7. 建设顺序与未决项

| 阶段 | 可交付结果 | 依赖及边界 |
|---|---|---|
| A 已完成的设计基线 | 20 频道、三播出日、六态、人机交接、深浅主题的本地原型 | 虚构记录，不等于后台能力 |
| B 状态基础 | 数据库、事件规则、只读快照接口；刷新／重启保留状态，样例源和真实源隔离 | 可先用构造事件验证；不冒称真实编单 |
| C 逐源接入 | EPG、执行器、Output、人工及 Playbox 证据逐项接入 | 依赖 E18、E12 和实际编单节点；未接入来源如实显示未知 |
| D 内网交付 | 离线安装包、现场大屏、故障恢复及备份演练 | E07、E13、E19；完整编单还需已有其他验证项 |

当前可以继续细化 B 的实现合同；本文不等于批准所有后台立即开工。首批频道真实名录与时区、每日计划例外、人工信号、Playbox 接收证据、机器架构和恢复时限待确认。当前优先调研及云端模型评估，基本方案确定后再展开安全与实现，顺序以行动计划为准；最终网站独立内网运行不能由云端演示替代。

验收方法统一维护在[验证计划第 13 节](../planning/02-前期探索与验证计划.md#13-浏览器大屏e19)；当前结果及缺口由[台账](../planning/07-产品决策与验证台账.md)维护。

## 8. 长期展示与可读性

这块屏幕需要经过开机、休眠恢复、浏览器重启、午夜换日和持续展示的实际验证；具体终端设置由内网维护人员一次性配置，日常观众无需操作。持续动画与自动变化应分别评估是否需要暂停机制，参照 [W3C 暂停／停止准则](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)；现有按钮不能直接被认定为全面符合性证明。

频道编号和文字应在深浅两种背景、微闪最暗帧和实际观看距离下可辨。状态除颜色外还需有可见文字／形状及辅助技术名称；关键故障编号在辅助摘要可识别，不能要求悬停才能知道，具体小标记在真实接入阶段保持既有风格验证。颜色要求参照 [W3C 颜色准则](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)，本次不改原型外观。

故障“较急促”不等于任意加速或全屏闪红，必须核验组合闪烁与对比度。相关验证补入 E19；未测量前不宣称完整可访问性通过。技术依据及本轮发现见[开发核查记录](../research/07-大屏内网网站开发核查.md)。
