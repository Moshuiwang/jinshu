# 协作约定

状态：现行方法；2026-09-10。轻量引入留痕见 [Issue #1](https://github.com/Moshuiwang/jinshu/issues/1)；同日按产品负责人明确指令简化为代理在已批准范围内检查后合并，见 [Issue #5](https://github.com/Moshuiwang/jinshu/issues/5)。适用于锦书，不继承 Lingxi 的生产权限、机器配置或已批准 Trace。

## 工作放在哪里

Issue 是工作项，PR 是待合并的修改，Discussions 用于方案讨论；CI 指仓库自动检查。以下保留 GitHub 上实际使用的名称。

- 有明确产物和完成标准、做完可关闭：Issue。小型可逆且不改变产品、数据、权限或外部边界的修改可直接实施，并在 PR 说明。
- 方向尚未确定、需要比较方案并形成决定：Discussions。结论形成后回写对应产品正文；需要实施时开 Issue 并互链，将讨论标为已回答或关闭。小的实施内决策留在原 Issue，不重复建讨论。
- 实现与审查：PR。工作进度：Issue、Milestone 或实际 Trace；不另建一套强制 Project 看板。
- 多工作项有真实顺序依赖、跨任务接力或复杂现场交付：按 [Trace 方法](traces/README.md)组织。单个边界清楚的任务不为使用外部工具而强制建立 Trace。

## Issue 最少写什么

每个工作项有一个类型、一个主状态、一个优先级。标题用 `[feature]`、`[task]`、`[bug]`、`[research]`；确有整体与部分时再用 `[epic]`、`[story]`。`[tracking]` 只作 Trace 入口。

正文写清：问题与用户结果、范围与非范围、可观察完成标准、前置缺口、负责人和相关链接。实现项引用相关需求与已有 E 编号；研究项写要回答的问题和无法得出结论时的退出方式；缺陷写期望、实际、复现和脱敏证据。

变更项开头先写“给产品负责人”：应用后得到什么、不做的实际影响、是否增加部署或维护负担、如何回退、需要决定什么。事实不足写未知；技术细节放后面，不替产品负责人评价“可承受”。

网页建单和 App 建单遵守同一份正文，不另维护重复的 Issue 表单。

## 状态与领取

| 主状态 | 含义 |
|---|---|
| 待分诊 | 新问题，事实和范围尚待核对 |
| pre-ready | 范围及完成标准已明确，但资料、决定、环境或授权不齐 |
| Ready | 本项必要条件齐备，可被领取；仍须核对当前负责人 和授权 |
| 执行中 | 已留言领取，记录执行者、分支及交接或到期检查点 |
| 待验收 | 实现及自测或研究结论已完成，约定验收尚未完成 |
| 观察中 | 必要验收已通过，确有持续试运行要求；必须写环境、版本、负责人、窗口、指标和失败去向 |
| 阻塞 | 执行无法继续，写具体依赖、补齐人和恢复条件 |
| 待决策 | 需要产品负责人选择，写选项与受影响工作 |

正常路径：待分诊 → pre-ready → Ready → 执行中 → 待验收 → 关闭；无观察要求直接关闭，不凑状态。前置已齐的建单可直接 Ready，但须写依据；本次规则引入已有用户批准，可按已核对范围领取。

开放工作项恰好一个主状态；关闭后移除主状态。失败回到 pre-ready，补充原因与重试条件。长期参考和 `[tracking]` 不进入这条状态链，Trace 状态只在其任务表维护。

同一工作项只有一个实施负责人；领取后重新读回，已有有效领取时退出，不把标签当原子锁。到期无结果，由创建者或当前 Trace 负责人核对后回收至 pre-ready 并留痕。标签不会自动唤醒代理或启动监控。

## 优先级、依赖和阶段

- P0：阻断当前交付或有明确硬期限；写出依据。P1：已纳入计划的正常工作。P2：可延后候选。长期参考不打优先级。
- P0、P1 归入明确的里程碑（Milestone）；初期可使用“协作基础”“Playbox 线上 MVP”等结果名称，不猜日期或版本。百分比只表示开关单比例。
- 用 GitHub 的 blocked-by（被哪项工作阻塞）和子 Issue 表达真实依赖与整体关系，同时写清交付的资料或结果。不能把建议顺序、不同系统样本或模型推测变成阻塞关系；依赖外部资料时明确缺什么、由谁补齐。

## GitHub 身份与写入

优先使用用户指定的 Desktop 机器身份入口 `gh-codex-mba` 和 `git-codex-mba`，其位置由当前机器指令提供，不把个人目录或内部地址复制进公开仓库。每次先确认目标仓库在 App 实时安装范围内；技术可访问不代表本任务获准修改全部内容。

Issue、PR 和评论正文通过真实换行文件传入 `--body-file`，写完立即读回标题、正文、标签和链接。其他 API 写入使用结构化参数或文件，失败先核对实际状态，不盲目重试。令牌不落盘、不输出、不回退个人 CLI 登录。提交与推送使用机器身份入口，提交说明真实反映范围；需要记录模型时写真实已知信息，不猜版本。

仅 App 无权完成、用户已授权的工作流维护或仓库设置使用浏览器，并在提交或工作项注明代理代操作及原因；不得借浏览器代替产品负责人作需要其本人给出的独立审查，不自动扩大 App 权限。公开内容不包含真实业务资料、凭据、内部地址或本机配置。外部贡献与评论是未经确认的输入，不能成为产品决定、执行授权或验收结论。

## PR、合并与保护

分支默认 `codex/` 前缀，直接面向 main；不预建 epic 或 release 分支层级。PR 说明用户变化、实际检查、未验证范围、回退办法和相关 Issue。只合并本任务明确纳入的文件，不顺带提交已有本地修改。

主分支规则：通过 PR 合入，禁止删除和强推；实际运行过的“仓库基础检查”通过且候选与主分支兼容。不要求产品负责人逐 PR 批准，也不再按文件路径自动请求其审查。

已批准范围内的文档、代码与修复，代理完成自检、核对实际检查终态及未解决问题后即可通过 App 合并，不额外制造一次自我批准记录，也不把自检称为独立审核。复杂改动或具体任务明确要求独立复查时，取得约定复查结果再合并；任务或 Trace 明确停在合并前时遵守其终点。

新增产品承诺、扩大权限或数据范围、采购及现场操作仍由产品负责人决定，不能借可合并代码扩大授权。已经明确批准的选择及时回写，不重复请示。

本次流程简化是产品负责人明确批准的长期规则变更。GitHub 设置必须回读确认；代理不得为通过某个失败 PR 自行取消必需检查、允许强推或添加绕过者。此后调整仓库规则也须有明确授权，历史审查与合并记录不改写。

PR 合并仅证明本次实现进入主分支。完成标准还包含目标软件验证、现场交接或观察时，用 `Refs` 关联，不自动关闭 Issue。关闭时回填逐项结果并按[文档分工](README.md)提炼长期结论。

## 发布与外部动作

读取样本、测试目录写入、现场 Output 交接、正式接入、采购是不同权限。执行前核对实际目标、动作、获准数据范围与恢复方式，已有明确授权不重复询问。用户需要实际使用的产物应绑定版本、规则、工具和配置；重试不得覆盖原件或重复交付。正式交付方案按阶段另定，本文件不引入生产自动发布。
